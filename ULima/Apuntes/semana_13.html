Procedimientos Almacenados vs. Funciones UDF

En la ingeniería de bases de datos relacionales moderna (PostgreSQL 16/17, Oracle 23ai, SQL Server 2022), la distinción entre un Procedimiento Almacenado (PROCEDURE) y una Función Definida por el Usuario (FUNCTION) no es meramente semántica; radica en el control del contexto transaccional y la capacidad de invocación dentro del motor de consultas.

Característica Stored Procedure (PROCEDURE) User Defined Function (FUNCTION)
Propósito Primario Ejecutar procesos de negocio, orquestación de múltiples tablas y transformaciones complejas. Calcular y retornar un valor escalar o conjunto tabular a partir de entradas.
Control Transaccional (COMMIT/ROLLBACK) SÍ PERMITIDO. Puede iniciar, comitear y revertir transacciones internas de forma autónoma. ESTRICTAMENTE PROHIBIDO dentro de la función (ejecuta dentro de la transacción del llamador).
Invocación en sentencias SQL Se invoca con CALL sp_nombre(...). No se puede embeber en SELECT, WHERE o JOIN. Se puede llamar en cualquier expresión SQL: SELECT fn_calcular(x), * FROM t WHERE fn_filtro(y).
Valores de Retorno No tiene cláusula RETURNS. Devuelve valores mediante parámetros INOUT o OUT. Obligatorio RETURNS tipo_dato o RETURNS TABLE(...) o RETURNS SETOF.
Optimización del Optimizador Caja negra operacional para el planificador. Clasificable como IMMUTABLE, STABLE o VOLATILE para optimización y memoización de costos.

1. Stored Procedure con Transacción PostgreSQL / PL/pgSQL 
CREATE OR REPLACE PROCEDURE sp_transferir_fondos(
    p_origen_id INT,
    p_destino_id INT,
    p_monto NUMERIC(12,2)
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_saldo_actual NUMERIC(12,2);
BEGIN
    -- Bloqueo pesimista para evitar race conditions
    SELECT saldo INTO v_saldo_actual
    FROM cuentas
    WHERE cuenta_id = p_origen_id
    FOR UPDATE;

    IF v_saldo_actual < p_monto THEN
        RAISE EXCEPTION 'Saldo insuficiente: %', v_saldo_actual;
    END IF;

    UPDATE cuentas SET saldo = saldo - p_monto WHERE cuenta_id = p_origen_id;
    UPDATE cuentas SET saldo = saldo + p_monto WHERE cuenta_id = p_destino_id;

    -- Procedimiento puede ejecutar COMMIT explícito
    COMMIT;
END;
$$;
2. Table-Valued Function (UDF) PostgreSQL / PL/pgSQL 
CREATE OR REPLACE FUNCTION fn_resumen_cliente(
    p_cliente_id INT
)
RETURNS TABLE(
    total_pedidos BIGINT,
    monto_total NUMERIC(14,2),
    ticket_promedio NUMERIC(10,2)
)
LANGUAGE plpgsql
STABLE
AS $$
BEGIN
    RETURN QUERY
    SELECT 
        COUNT(pedido_id),
        COALESCE(SUM(total), 0.00),
        COALESCE(AVG(total), 0.00)
    FROM pedidos
    WHERE cliente_id = p_cliente_id;
END;
$$;

-- Invocable directamente en una consulta SELECT
SELECT c.nombre, f.* 
FROM clientes c
CROSS JOIN LATERAL fn_resumen_cliente(c.cliente_id) f;

Triggers: Ciclo de Vida, Disparadores y Mutaciones

Un Trigger (disparador) es un bloque de código procedimental compilado en el motor de base de datos que se ejecuta automáticamente como reacción ante un evento específico de manipulación de datos (DML: INSERT, UPDATE, DELETE) o definición (DDL: CREATE, DROP, ALTER).

🛡️ BEFORE (Antes)

Se ejecuta antes de que el registro se inserte o modifique en la tabla y antes de validar constraints referenciales. Ideal para validación, sanitización y mutación directa de campos (:NEW.columna := UPPER(:NEW.columna)). Retorna el registro a persistir.

📜 AFTER (Después)

Se ejecuta después de que los datos fueron escritos en los buffers y las llaves foráneas fueron satisfechas. Ideal para auditoría inmutable, replicación de eventos, recálculo de agregados en tablas satélite y notificaciones asíncronas (pg_notify).

🪟 INSTEAD OF (En Lugar De)

Se asocia exclusivamente a Vistas Complejas (Views) que contienen JOIN o agregaciones y que son inherentemente no actualizables. El trigger intercepta el DML y ejecuta las inserciones/actualizaciones en las tablas subyacentes.

Matriz de Registros Contextuales: OLD vs NEW

INSERT
  • OLD = NULL (No existía previo)
  • NEW = Registro a insertar
UPDATE
  • OLD = Estado previo en disco
  • NEW = Estado modificado propuesto
DELETE
  • OLD = Registro eliminado
  • NEW = NULL (No existe futuro)

⚠️ Concepto Clave de Examen: The Mutating Table Problem (Tabla Mutante)

El error de Tabla Mutante (clásico en Oracle como ORA-04091: table is mutating, trigger/function may not see it) ocurre cuando un trigger de fila (FOR EACH ROW) intenta consultar o modificar (SELECT / UPDATE) la misma tabla que actualmente está siendo afectada por la sentencia DML que disparó dicho trigger.

¿Por qué falla el motor?

Porque la tabla se encuentra en un estado inconsistente y transitorio en memoria; el motor no puede garantizar aislamiento de lectura ni consistencia de lectura determinista fila por fila.

Solución de Arquitectura

1. Usar Compound Triggers (Oracle) o Transition Tables con REFERENCING NEW TABLE AS new_tbl (PostgreSQL 10+ / Statement Level) para evaluar el conjunto completo consolidado.

Implementación de Élite: Auditoría Inmutable con Delta JSONB PostgreSQL 16/17 
-- 1. Tabla de Auditoría Inmutable (Append-Only)
CREATE TABLE log_auditoria (
    log_id BIGSERIAL PRIMARY KEY,
    nombre_tabla VARCHAR(64) NOT NULL,
    operacion VARCHAR(10) NOT NULL,
    usuario_db VARCHAR(64) DEFAULT CURRENT_USER,
    ip_cliente INET DEFAULT inet_client_addr(),
    fecha_registro TIMESTAMPTZ DEFAULT CLOCK_TIMESTAMP(),
    registro_previo JSONB,
    registro_nuevo JSONB,
    delta_cambios JSONB
);

-- 2. Función Trigger Genérica Reutilizable
CREATE OR REPLACE FUNCTION fn_trigger_auditoria_delta()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
DECLARE
    v_old_json JSONB := NULL;
    v_new_json JSONB := NULL;
    v_delta JSONB := NULL;
BEGIN
    IF (TG_OP = 'DELETE') THEN
        v_old_json := to_jsonb(OLD);
    ELSIF (TG_OP = 'INSERT') THEN
        v_new_json := to_jsonb(NEW);
    ELSIF (TG_OP = 'UPDATE') THEN
        v_old_json := to_jsonb(OLD);
        v_new_json := to_jsonb(NEW);
        -- Extrae únicamente los campos que sufrieron modificación
        SELECT jsonb_object_agg(n.key, n.value) INTO v_delta
        FROM jsonb_each(v_new_json) n
        WHERE n.value IS DISTINCT FROM (v_old_json -> n.key);
    END IF;

    INSERT INTO log_auditoria (nombre_tabla, operacion, registro_previo, registro_nuevo, delta_cambios)
    VALUES (TG_TABLE_NAME, TG_OP, v_old_json, v_new_json, v_delta);

    RETURN COALESCE(NEW, OLD);
END;
$$;

-- 3. Vinculación del Trigger AFTER en la tabla crítica
CREATE OR REPLACE TRIGGER tr_auditar_empleados
AFTER INSERT OR UPDATE OR DELETE ON empleados
FOR EACH ROW EXECUTE FUNCTION fn_trigger_auditoria_delta();

Triggers en BD vs. Change Data Capture (CDC / Kafka) en 2026

En la arquitectura de microservicios y sistemas de streaming de 2026, los Triggers tradicionales dentro de la base de datos están siendo complementados o reemplazados para eventos externos por Change Data Capture (CDC) mediante herramientas como Debezium, Kafka Connect y Redpanda. Comprender los trade-offs es vital para el diseño de sistemas distribuidos.

🏛️ In-Database Triggers (Síncronos)
  • Consistencia: 100% ACID garantizada en la misma transacción atómica.
  • Latencia: Cero latencia externa; ocurre dentro del ciclo del DML.
  • Desventaja Crítica: Genera contención de bloqueos (Lock Contention), degrada el TPS en escrituras masivas y puede causar cuellos de botella no escalables horizontalmente.
⚡ CDC Asíncrono (Debezium / Kafka WAL Reading)
  • Impacto en BD: Casi nulo (lee el Write-Ahead Log o Binary Log sin interferir con locks de tablas).
  • Escalabilidad: Desacopla consumidores (microservicios, Search Index, Lakehouse, Webhooks).
  • Desventaja: Consistencia eventual (latencia de propagación de milisegundos).

🎯 Perspectivas Profesionales & Literatura Canónica

Análisis técnico aplicado según los perfiles de la industria y fundamentos de textos clásicos de bases de datos.

🏛️ Arquitecto de Datos

Transaccionalidad Atómica y Preservación de Invariantes Relacionales

Los triggers y procedimientos almacenados constituyen el último bastión de consistencia cuando los constraints declarativos (CHECK, FOREIGN KEY) resultan insuficientes. El Arquitecto diseña la jerarquía de eventos para garantizar que las transacciones respeten invariantes multi-tabla sin generar condiciones de carrera. Los triggers BEFORE se reservan para validación y sanitización en memoria antes de persistir en WAL, impidiendo mutaciones secundarias descontroladas.

📖 Referencia: Silberschatz, Korth & Sudarshan — Database System Concepts (7th Ed.), Cap. 5: Advanced SQL & Integrity Constraints
⚙️ Ingeniero de Datos

Mitigación de Tablas Mutantes, Cascading Hell y Auditoría Delta JSONB

Los triggers que consultan o mutan la misma tabla en ejecución generan errores de tabla mutante (ORA-04091) o contención severa de bloqueos (RowExclusiveLock), degradando el TPS transaccional. La solución senior consiste en migrar a triggers por sentencia con tablas de transición (REFERENCING NEW TABLE) o serializar el diff operacional en columnas JSONB de auditoría, aislando por completo la mutación del histórico de cambios.

📖 Referencia: Bill Karwin — SQL Antipatterns, Cap. 18: Spaghetti Query & Cap. 12: Phantom Updates
☁️ Ingeniero Cloud & MDS

De Triggers Síncronos a Event-Driven CDC con Kafka y Debezium

Invocar llamadas de red HTTP o replicar datos analíticos dentro de un trigger síncrono bloquea la transacción principal y vulnera la disponibilidad del servicio. En arquitecturas modernas de 2026, los eventos de dominio se propagan mediante Change Data Capture (CDC) no intrusivo con Debezium leyendo el Write-Ahead Log (WAL) hacia Apache Kafka, desacoplando consumidores analíticos (Snowflake, Elasticsearch) sin penalizar el motor OLTP.

📖 Referencia: Martin Kleppmann — Designing Data-Intensive Applications, Cap. 11: Stream Processing & The Log Primitive

Regla de Oro en Producción

Usa BEFORE triggers para modificar los datos de la misma fila sin overhead. Usa AFTER triggers solo para sincronizar otras tablas o auditoría. Nunca invoques servicios web HTTP síncronos dentro de un trigger.
