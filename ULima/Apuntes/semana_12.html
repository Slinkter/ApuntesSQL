  • Utilizar tipado dinámico seguro con variables ancla %TYPE y %ROWTYPE, así como estructuras de control IF, CASE, FOR IN QUERY y FOREACH.
  • Dominar el ciclo de vida completo de Cursores explícitos y parametrizados, ejecutando actualizaciones posicionales con WHERE CURRENT OF.
  • Diferenciar con precisión arquitectónica Functions (consultas y expresiones) de Stored Procedures (control transaccional autónomo con `COMMIT`/`ROLLBACK`).
  • Construir Triggers de auditoría forense (Change Data Capture en JSONB) y validación de reglas de negocio con variables de contexto NEW, OLD y TG_OP.
  • Implementar SQL dinámico inmune a SQL Injection mediante EXECUTE format('%I', ...) USING ... y manejo de excepciones con SQLSTATE.

1. Anatomía de Bloques, Variables y Tipado Fuerte

PL/pgSQL es un lenguaje procedimental estructurado en bloques jerárquicos. Permite ejecutar lógica de negocio directamente dentro del proceso del motor de base de datos, eliminando la latencia de red (network round-trips) de múltiples consultas individuales.

/* ESTRUCTURA FORMAL DE UN BLOQUE PL/pgSQL */
[ <<etiqueta_bloque>> ]
[ DECLARE
    -- Declaración de variables, constantes, tipos ancla (%TYPE, %ROWTYPE), cursores
    v_id          INTEGER := 100;
    v_salario     empleados.salario%TYPE;      -- Hereda tipo exacto de columna
    v_emp_row     empleados%ROWTYPE;           -- Registro completo de la tabla
    v_cursor      CURSOR FOR SELECT ...;
]
BEGIN
    -- Cuerpo ejecutable: Sentencias SQL, bucles, condicionales, llamadas
    SELECT * INTO v_emp_row FROM empleados WHERE emp_id = v_id;
    
    IF v_emp_row.salario < 3000 THEN
        v_salario := v_emp_row.salario * 1.15;
    END IF;

[ EXCEPTION
    -- Manejo de errores (Crea subtransacción/Savepoint implícito)
    WHEN NO_DATA_FOUND THEN
        RAISE NOTICE 'Empleado % no encontrado', v_id;
    WHEN OTHERS THEN
        RAISE EXCEPTION 'Error inesperado: % (Código: %)', SQLERRM, SQLSTATE;
]
END [ etiqueta_bloque ];

Tipos de Datos Especiales y Variables Ancla

tabla.columna%TYPE Garantiza que la variable cambie automáticamente su tipo de dato si la columna en la tabla es modificada en el esquema (evita bugs por refactorización).
tabla%ROWTYPE Estructura de registro compuesta por todas las columnas de la tabla. Permite almacenar el resultado completo de un `SELECT * INTO row_var`.
RECORD Tipo genérico no estructurado a priori; adquiere la estructura de columnas de la consulta que se le asigne durante la ejecución en tiempo de corrida.

2. Control de Flujo, Bucles y Gestión de Cursores

/* DIAGRAMA ASCII: Ciclo de Vida y Manipulación de un Cursor */
1. DECLARE cur CURSOR FOR SELECT ... FOR UPDATE;
       ↓
2. OPEN cur;                    <-- El motor materializa/prepara el plan de consulta
       ↓
3. FETCH NEXT FROM cur INTO var; <-- Recupera la tupla actual y avanza el puntero
       ↓
   ¿FOUND = TRUE?
    ├── SI: Procesar datos -> UPDATE tabla SET ... WHERE CURRENT OF cur; -> Repetir FETCH
    └── NO: Fin del conjunto (EOF)
       ↓
4. CLOSE cur;                   <-- Libera memoria de trabajo (Portal buffers)
-- Actualización Posicional Segura con Cursor y FOR UPDATE
DO $$
DECLARE
    cur_cuentas CURSOR FOR 
        SELECT cuenta_id, saldo 
        FROM cuentas 
        WHERE estado = 'ACTIVA' AND saldo < 100 
        FOR UPDATE; -- Bloqueo pesimista de tuplas en el cursor
    v_cuenta_id INT;
    v_saldo NUMERIC(12,2);
BEGIN
    OPEN cur_cuentas;
    LOOP
        FETCH NEXT FROM cur_cuentas INTO v_cuenta_id, v_saldo;
        EXIT WHEN NOT FOUND;

        -- Cargo administrativo a cuentas de bajo saldo
        UPDATE cuentas 
        SET saldo = saldo - 5.00,
            ultima_modificacion = clock_timestamp()
        WHERE CURRENT OF cur_cuentas; -- Modificación posicional directa sin re-escaneo
    END LOOP;
    CLOSE cur_cuentas;
END $$;

3. Functions vs Stored Procedures: La Frontera Transaccional

Característica User-Defined Function (CREATE FUNCTION) Stored Procedure (CREATE PROCEDURE)
Invocación SELECT mi_funcion(args); (en SELECT, WHERE, JOIN). CALL mi_procedimiento(args);
Retorno de Valor Obligatorio: retorna un valor escalar, TABLE(...) o SETOF. Opcional: no retorna valor directo; usa parámetros INOUT.
Gestión Transaccional NO PUEDE ejecutar COMMIT o ROLLBACK. Corre dentro de la transacción externa. SÍ PUEDE ejecutar COMMIT y ROLLBACK explícitos en tiempo de ejecución.
Propiedades de Optimización IMMUTABLE, STABLE, VOLATILE, PARALLEL SAFE. No aplican atributos de volatilidad funcional.
-- Procedimiento Almacenado con Gestión Transaccional Batch y COMMIT Autónomo
CREATE OR REPLACE PROCEDURE sp_procesar_pagos_masivos(
    p_lote_id INT,
    INOUT p_procesados INT DEFAULT 0,
    INOUT p_fallidos INT DEFAULT 0
)
LANGUAGE plpgsql
AS $$
DECLARE
    rec RECORD;
BEGIN
    FOR rec IN 
        SELECT pago_id, cliente_id, monto 
        FROM pagos_pendientes 
        WHERE lote_id = p_lote_id 
    LOOP
        BEGIN
            -- Descontar saldo del cliente
            UPDATE clientes 
            SET saldo = saldo - rec.monto 
            WHERE cliente_id = rec.cliente_id AND saldo >= rec.monto;

            IF NOT FOUND THEN
                RAISE EXCEPTION 'Saldo insuficiente para cliente %', rec.cliente_id;
            END IF;

            -- Registrar pago exitoso
            INSERT INTO pagos_procesados(pago_id, fecha_pago) VALUES (rec.pago_id, NOW());
            DELETE FROM pagos_pendientes WHERE pago_id = rec.pago_id;

            p_procesados := p_procesados + 1;

            -- Commit por lotes cada 1000 registros para no saturar WAL ni bloqueos
            IF p_procesados % 1000 = 0 THEN
                COMMIT; -- ¡Solo permitido en CREATE PROCEDURE!
            END IF;

        EXCEPTION WHEN OTHERS THEN
            p_fallidos := p_fallidos + 1;
            INSERT INTO logs_errores(pago_id, mensaje, fecha) 
            VALUES (rec.pago_id, SQLERRM, NOW());
            -- Subtransacción implícita revierte solo este registro
        END;
    END LOOP;
    
    COMMIT; -- Commit final
END;
$$;

4. Triggers Avanzados: Validación de Negocio y Auditoría CDC con JSONB

/* VARIABLES ESPECIALES DISPONIBLES EN TRIGGER FUNCTIONS */
- NEW           : Registro con los nuevos valores (INSERT, UPDATE). En DELETE es NULL.
- OLD           : Registro con los valores previos (UPDATE, DELETE). En INSERT es NULL.
- TG_OP         : Operación actual ('INSERT', 'UPDATE', 'DELETE', 'TRUNCATE').
- TG_TABLE_NAME : Nombre de la tabla sobre la que se disparó el trigger.
- TG_WHEN       : Momento de ejecución ('BEFORE', 'AFTER', 'INSTEAD OF').
- TG_LEVEL      : Nivel de ejecución ('ROW' o 'STATEMENT').
-- Trigger de Auditoría Universal CDC (Change Data Capture) con Payload JSONB
-- 1. Tabla de Auditoría Genérica
CREATE TABLE auditoria_general (
    audit_id BIGSERIAL PRIMARY KEY,
    esquema_nombre TEXT NOT NULL,
    tabla_nombre TEXT NOT NULL,
    operacion TEXT NOT NULL,
    usuario_db TEXT NOT NULL DEFAULT session_user,
    datos_previos JSONB,
    datos_nuevos JSONB,
    fecha_evento TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

-- 2. Función Trigger Reutilizable
CREATE OR REPLACE FUNCTION trg_fn_auditoria_universal()
RETURNS TRIGGER 
LANGUAGE plpgsql
SECURITY DEFINER -- Ejecuta con privilegios del creador para asegurar escritura en audit
SET search_path = pg_catalog, public
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO auditoria_general(esquema_nombre, tabla_nombre, operacion, datos_nuevos)
        VALUES (TG_TABLE_SCHEMA, TG_TABLE_NAME, TG_OP, to_jsonb(NEW));
        RETURN NEW;
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO auditoria_general(esquema_nombre, tabla_nombre, operacion, datos_previos, datos_nuevos)
        VALUES (TG_TABLE_SCHEMA, TG_TABLE_NAME, TG_OP, to_jsonb(OLD), to_jsonb(NEW));
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO auditoria_general(esquema_nombre, tabla_nombre, operacion, datos_previos)
        VALUES (TG_TABLE_SCHEMA, TG_TABLE_NAME, TG_OP, to_jsonb(OLD));
        RETURN OLD;
    END IF;
    RETURN NULL;
END;
$$;

-- 3. Vincular Trigger a la tabla de Empleados
CREATE TRIGGER trg_auditar_empleados
AFTER INSERT OR UPDATE OR DELETE ON empleados
FOR EACH ROW
EXECUTE FUNCTION trg_fn_auditoria_universal();

5. Seguridad Defensiva y SQL Dinámico en Producción (2026)

🛡️ Regla de Oro: SQL Dinámico con format() y Cláusula USING

Nunca concatene cadenas de texto de usuario directamente en una sentencia EXECUTE. Utilice format('%I', identificador) para tablas/columnas y la cláusula USING valor para parámetros escalares.

❌ Vulnerable a Inyección SQL: 
-- ¡Inseguro! Concatenación directa
v_sql := 'SELECT * FROM ' || p_tabla || 
         ' WHERE usuario = ''' || p_user || '''';
EXECUTE v_sql;
✅ Sanitizado y Seguro (Estándar 2026): 
-- Seguro: %I para tablas, USING para valores
v_sql := format('SELECT * FROM %I WHERE usuario = $1', p_tabla);
EXECUTE v_sql USING p_user;

Conceptos Clave

  • § %TYPE & %ROWTYPE Tipado ancla acoplado al esquema que previene desajustes de tipos.
  • § Cursor & WHERE CURRENT OF Control de iteración y modificaciones directas sin re-escaneo de índice.
  • § Function vs Procedure Functions retornan valor; Procedures controlan transacciones (`COMMIT`).
  • § Triggers NEW & OLD Variables contextuales de tuplas antes y después del evento DML.
  • § Change Data Capture (CDC) Auditoría reactiva serializando tuplas a JSONB en caliente.
  • § format('%I') & USING Inmunidad contra inyecciones en SQL dinámico de servidor.
