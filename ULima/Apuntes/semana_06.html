📐 Mapeo DER a Modelo Relacional

Entidades fuertes → Tablas con PK | Relaciones 1:N → FK en lado N | Relaciones N:M → Tabla puente intermedia | Multivaluados → Tabla hija.

🏛️ Principios de Arquitectura: La Frontera Conceptual vs Lógica

El Diagrama Entidad-Relación (DER) es un modelo semántico puro independiente de la tecnología. En el DER no existen "Foreign Keys", ni tipos de datos físicos (como VARCHAR(50) o INT4), ni índices B-Tree. Las relaciones se expresan como vínculos abstractos con cardinalidades de negocio.

El Diseño Lógico es el puente matemático donde el DER se mapea formalmente a relaciones (tablas), transformando las relaciones 1:N en claves foráneas y las relaciones M:N en tablas intermedias de unión.

Objetivos y Competencias de la Semana

  • Identificar y clasificar entidades fuertes, entidades débiles y entidades asociativas.
  • Modelar atributos simples, compuestos, multivaluados, derivados y claves identificadoras.
  • Definir cardinalidades estructurales (1:1, 1:N, M:N) y restricciones de participación (Total vs Parcial).
  • Construir jerarquías de generalización y especialización (Supertipos y Subtipos) analizando restricciones de disyunción y completitud.
  • Aplicar el algoritmo de mapeo estándar para convertir un DER/EER a un esquema relacional PostgreSQL 16 sin pérdida semántica.

1. Componentes Nucleares del Modelo E-R

1.1 Entidades Fuertes vs Entidades Débiles

Una Entidad es cualquier objeto, persona, concepto o evento del mundo real distinguible de los demás sobre el cual el negocio necesita registrar datos.

🔵 Entidad Fuerte (Regular)

Existe de forma autónoma en el dominio del negocio. Posee una clave primaria propia (atributo o conjunto de atributos) que identifica unívocamente a cada una de sus instancias sin depender de ninguna otra entidad.

Representación Chen: Rectángulo simple
Ejemplo: CLIENTE(id_cliente, nombre, ruc)

🔴 Entidad Débil

No puede existir sin la entidad fuerte de la cual depende (dependencia de existencia) y carece de clave primaria propia. Solo se identifica combinando la clave de la entidad fuerte con su discriminador o clave parcial (dependencia de identificación).

Representación Chen: Rectángulo doble & Relación identificadora en rombo doble
Discriminador: Subrayado punteado (- - -)
Ejemplo: DEPENDIENTE(id_empleado, num_hijo, nombre)

1.2 Clasificación Taxonómica de Atributos

Tipo de Atributo Definición Formal Símbolo Chen Regla de Mapeo Relacional
Simple (Atómico) No divisible en componentes menores (ej. precio, dni). Elipse simple Se convierte directamente en una columna de la tabla.
Compuesto Jerarquía de subatributos (ej. direccion → calle, numero, distrito). Elipse con ramas Se aplana incluyendo únicamente sus hojas atómicas como columnas.
Multivaluado Puede contener múltiples valores para una misma instancia (ej. telefonos). Elipse doble Requiere tabla independiente con la PK del padre + el valor multivaluado.
Derivado Calculable a partir de otros datos (ej. edad = CURRENT_DATE - fecha_nac). Elipse punteada No se almacena físicamente (o se calcula en Vistas / Generated Columns).

2. Relaciones, Cardinalidad y Participación

Una relación representa una asociación semántica entre dos o más entidades. Se caracteriza por su Razón de Cardinalidad (máximo número de instancias asociadas) y su Restricción de Participación (mínimo número de instancias asociadas).

Notación Chen
EMPLEADO (1,1) ── DIRIGE ── (0,1) DEPARTAMENTO

(Mínimo, Máximo): Un empleado puede dirigir de 0 a 1 depto; un depto es dirigido por exactamente 1 empleado.

3. Jerarquías de Especialización y Generalización (EER)

El Modelo Entidad-Relación Extendido (EER) introduce el modelado de herencia. Un Supertipo contiene los atributos comunes, mientras que los Subtipos heredan dichos atributos y añaden características exclusivas.

MATRIZ DE RESTRICCIONES EN JERARQUÍAS EER
Disjunta (Disjoint 'd') Solapada (Overlapping 'o')
Total (Doble Línea =) Una instancia DEBE ser EXACTAMENTE UNO de los subtipos. (Sin otros tipos). Una instancia DEBE ser AL MENOS UNO o VARIOS subtipos simultáneamente.
Parcial (Línea Simple) Una instancia PUEDE no ser ningún subtipo (permanece solo en el supertipo). Una instancia PUEDE no ser ningún subtipo o ser VARIOS a la vez.

Ejemplo Disjunta Total: PERSONA → [CLIENTE, EMPLEADO] (Toda persona en BD debe ser Cliente O Empleado, no ambos).

Ejemplo Solapada Parcial: EMPLEADO → [INGENIERO, ADMINISTRATIVO] (Un empleado puede ser solo Empleado, o ser Ingeniero Y Administrativo).

4. Estrategias de Mapeo Relacional de Supertipos/Subtipos

Estrategia 1: Single Table Inheritance (Tabla Única)

Una sola tabla con todos los atributos del supertipo y subtipos, más una columna tipo_discriminador. Columnas de subtipos deben ser NULL.

Ventaja: Cero JOINs en consultas. Desventaja: Desperdicio de espacio por NULLs y pérdida de constraints NOT NULL.

Estrategia 2: Class Table Inheritance (Tabla por Clase / Normalizado) ⭐

Una tabla para el supertipo y una tabla separada por cada subtipo. La PK de cada subtipo es a la vez FK que referencia a la PK del supertipo (1:1).

Ventaja: 100% normalizado (3FN), permite constraints NOT NULL estrictas. Desventaja: Requiere JOINs para obtener todos los datos.

Estrategia 3: Concrete Table Inheritance (Tabla por Subtipo Concreto)

No se crea tabla para el supertipo. Se crea una tabla para cada subtipo repitiendo todas las columnas comunes del supertipo.

Ventaja: Consultas sin JOINs para subtipos específicos. Desventaja: Imposible garantizar unicidad global de claves y duplicación de DDL.

5. Caso de Estudio Completo: Sistema de Gestión Hospitalaria

-- 1. Supertipo: PERSONA CREATE TABLE persona ( id_persona INTEGER PRIMARY KEY GENERATED ALWAYS AS IDENTITY, dni VARCHAR(8) NOT NULL UNIQUE, nombres VARCHAR(100) NOT NULL, apellidos VARCHAR(100) NOT NULL, fecha_nacimiento DATE NOT NULL, telefono VARCHAR(15) ); -- 2. Subtipo 1: PACIENTE (Class Table Inheritance) CREATE TABLE paciente ( id_persona INTEGER PRIMARY KEY REFERENCES persona(id_persona) ON DELETE CASCADE, numero_seguro VARCHAR(20) NOT NULL UNIQUE, grupo_sanguineo VARCHAR(5) NOT NULL CHECK (grupo_sanguineo IN ('O+', 'O-', 'A+', 'A-', 'B+', 'B-', 'AB+', 'AB-')) ); -- 3. Subtipo 2: MEDICO (Class Table Inheritance) CREATE TABLE medico ( id_persona INTEGER PRIMARY KEY REFERENCES persona(id_persona) ON DELETE CASCADE, numero_colegiatura VARCHAR(10) NOT NULL UNIQUE, especialidad VARCHAR(50) NOT NULL ); -- 4. Entidad Fuerte: CONSULTA_MEDICA CREATE TABLE consulta_medica ( id_consulta INTEGER PRIMARY KEY GENERATED ALWAYS AS IDENTITY, id_paciente INTEGER NOT NULL REFERENCES paciente(id_persona), id_medico INTEGER NOT NULL REFERENCES medico(id_persona), fecha_hora TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP, diagnostico TEXT, costo NUMERIC(10,2) NOT NULL CHECK (costo >= 0) ); -- 5. Entidad Débil: RECETA_ITEM (Dependiente de CONSULTA_MEDICA) CREATE TABLE receta_item ( id_consulta INTEGER NOT NULL REFERENCES consulta_medica(id_consulta) ON DELETE CASCADE, item_nro SMALLINT NOT NULL, medicamento VARCHAR(100) NOT NULL, dosis VARCHAR(50) NOT NULL, frecuencia VARCHAR(50) NOT NULL, PRIMARY KEY (id_consulta, item_nro) );

🏛️ Arquitecto de Datos

Abstracción EER y Mapeo Algorítmico de Jerarquías

En el modelo Entidad-Relación Extendido (EER), el arquitecto formaliza restricciones de disyunción (Disjoint vs Overlapping) y completitud (Total vs Partial). La selección estratégica entre Single Table (TPH), Class Table (TPT) o Concrete Table (TPC) equilibra la pureza de 3FN con el costo computacional de joins, preservando la identidad semántica de entidades débiles y subtipos.

📖 Referencia: Elmasri & Navathe — Fundamentals of Database Systems (7ma Ed.), Caps. 3 y 4: "EER Modeling".
⚙️ Ingeniero de Datos

Antipatrón EAV vs Columnas Semi-estructuradas JSONB

Implementar el antipatrón Entity-Attribute-Value (EAV) ante atributos dinámicos destruye la integridad de tipos y degrada el motor forzando decenas de self-joins. El ingeniero moderno implementa esquemas híbridos en PostgreSQL utilizando columnas JSONB indexadas con operadores GIN (jsonb_path_ops), manteniendo validación y velocidad B-Tree en columnas críticas.

📖 Referencia: Bill Karwin — SQL Antipatterns: Avoiding the Pitfalls of Database Programming, Cap. 6: "EAV".
☁️ Ingeniero Cloud & MDS

Persistencia Políglota: Relacional, Documental y Grafos

En arquitecturas cloud nativas 2026, el modelo conceptual guía la distribución políglota: el núcleo transaccional reside en PostgreSQL/Aurora, los agregados altamente anidados se persisten en almacenes de documentos (MongoDB Atlas/DynamoDB), y las relaciones M:N altamente navegables se delegan a grafos nativos (Amazon Neptune, Neo4j) con adyacencia libre de índices.

📖 Referencia: AWS Storage Architecture Patterns: Polyglot Persistence & Graph Engines (2026).
