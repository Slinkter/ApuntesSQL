Teorema CAP, PACELC y el Paradigma BASE

En sistemas distribuidos, el Teorema CAP (Brewer) demuestra que ante una partición de red inevitable (Partition Tolerance), el sistema debe elegir entre consistencia estricta (Consistency) o disponibilidad ininterrumpida (Availability). El teorema PACELC amplía esta regla: "Si hay Partición (P), elige Disponibilidad (A) o Consistencia (C); si no hay partición (Else), elige Latencia (L) o Consistencia (C)".

Propiedad ACID (Relacional Tradicional) BASE (NoSQL Distribuido)
Consistencia Fuerte (Inmediata). Toda lectura ve la última escritura atómica confirmada. Eventual. Las réplicas convergen asíncronamente con el tiempo.
Disponibilidad Pesimista. Bloquea escrituras si hay riesgo de partición o split-brain. Básicamente Disponible (Basically Available). Responde siempre, aun con datos stale.
Escalabilidad Vertical principalmente (CPU/RAM). Sharding complejo. Horizontal nativa sobre miles de nodos commodity (Scale-out).

Las 4 Familias NoSQL y Casos de Uso Empresariales

📄 1. Document-Oriented (JSON/BSON)

Motores: MongoDB, PostgreSQL JSONB, Couchbase.
Estructura: Documentos semiestructurados auto-contenidos y anidados.
Caso Ideal: Catálogos de productos polimórficos, perfiles de usuario, CMS.

🔑 2. Key-Value (Clave-Valor)

Motores: Redis, AWS DynamoDB, Memcached.
Estructura: Acceso $O(1)$ por clave única con estructuras en memoria (Hashes, Sets, Lists).
Caso Ideal: Gestión de sesiones HTTP, caching ultra-rápido (< 1ms), rate limiting.

📊 3. Wide-Column & Columnar OLAP

Motores: Apache Cassandra, ScyllaDB, ClickHouse, DuckDB.
Estructura: Almacenamiento contiguo por columnas con compresión extrema.
Caso Ideal: Time-series IoT, telemetría masiva, métricas financieras en tiempo real.

🕸️ 4. Graph Databases (Grafos)

Motores: Neo4j, Amazon Neptune, Apache AGE.
Estructura: Nodos (Entidades) y Aristas (Relaciones con propiedades).
Caso Ideal: Detección de fraudes financieros circulares, grafos de conocimiento, Graph RAG.

Bases de Datos Vectoriales, pgvector e Índices HNSW

En la era de los Modelos de Lenguaje (LLMs) y la Generación Aumentada por Recuperación (RAG), las bases de datos deben almacenar y buscar Embeddings Vectoriales de alta dimensión ($d \in [768, 1536]$). La extensión pgvector permite a PostgreSQL realizar búsquedas semánticas híbridas con algoritmos de grafos aproximados (HNSW: Hierarchical Navigable Small World).

Implementación SQL: Vector Search con HNSW en PostgreSQL 16/17 pgvector 0.7+ 
CREATE EXTENSION IF NOT EXISTS vector;

-- 1. Tabla de Documentos y Embeddings Semánticos
CREATE TABLE base_conocimiento_rag (
    doc_id BIGSERIAL PRIMARY KEY,
    titulo VARCHAR(255) NOT NULL,
    contenido_texto TEXT NOT NULL,
    embedding VECTOR(1536) NOT NULL -- Dimensiones OpenAI / Claude
);

-- 2. Índice HNSW para Búsqueda Vectorial en Milisegundos con Distancia Coseno (<=>)
CREATE INDEX idx_rag_embedding_hnsw 
ON base_conocimiento_rag 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- 3. Consulta de Búsqueda Semántica por Similitud Coseno (Top 5)
SELECT 
    doc_id,
    titulo,
    1 - (embedding <=> '[0.012, -0.045, ...]'::VECTOR(1536)) AS similitud_coseno
FROM base_conocimiento_rag
ORDER BY embedding <=> '[0.012, -0.045, ...]'::VECTOR(1536)
LIMIT 5;
