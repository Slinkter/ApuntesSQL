Fundamentos: OLTP vs. OLAP y Enfoques de Diseño

Los sistemas OLTP (Online Transaction Processing) están optimizados para transacciones atómicas de alta concurrencia, minimizando redundancia mediante Tercera Forma Normal (3FN). Por el contrario, los sistemas OLAP (Online Analytical Processing) están diseñados para escaneos masivos, agregaciones temporales y análisis multidimensional, empleando Modelado Dimensional Desnormalizado.

Dimensión OLTP (Transaccional) OLAP (Data Warehouse)
Objetivo Principal Operación diaria del negocio en tiempo real (CRUD, POS, Web). Soporte para toma de decisiones estratégicas, BI y reporting.
Modelo de Datos ER altamente normalizado (3FN / BCNF). Cero redundancia. Dimensional (Star Schema / Snowflake). Tablas desnormalizadas.
Patrón de Acceso Muchas escrituras y lecturas de pocos registros por llaves primarias. Cargas batch masivas (Append) y consultas complejas de agregación (SUM, AVG).
Horizonte Temporal Datos actuales (semanas/meses). Purgas periódicas. Histórico completo (5 a 10+ años de snapshot inmutable).

📐 El Proceso de 4 Pasos de Ralph Kimball para el Diseño Dimensional

1
Seleccionar el Proceso

Elegir la actividad operativa del negocio (ej. Ventas, Facturación, Envíos, Reclamos).

2
Declarar la Granularidad

Definir qué representa exactamente UNA fila en la tabla de hechos (ej. "Un ítem individual de una orden").

3
Identificar Dimensiones

Determinar el contexto "quién, cuándo, dónde y qué" (Tiempo, Cliente, Producto, Tienda).

4
Identificar Hechos

Definir las métricas cuantitativas aditivas (Cantidad vendida, Monto de venta, Descuento aplicado).

Tipología Avanzada de Dimensiones y Tablas de Hechos

🌐 Dimensiones Conformadas (Conformed Dimensions)

Dimensiones idénticas o subconjuntos consistentes compartidos entre múltiples Data Marts (ej. Dim_Cliente o Dim_Tiempo compartida por Ventas, Envíos e Inventario). Permite el análisis cross-funcional (Kimball Enterprise Bus Matrix).

🎭 Role-Playing Dimensions

Una misma tabla física de dimensión que asume múltiples roles conceptuales en la misma Fact Table mediante alias en vistas o SQL (ej. Dim_Tiempo se vincula como fecha_pedido_key, fecha_envio_key y fecha_entrega_key).

🗑️ Junk Dimensions (Dimensión Basura)

Agrupación de múltiples indicadores, flags booleanos y códigos de estado dispersos (ej. es_promocion, tipo_pago, metodo_entrega) en una única dimensión combinatoria para evitar tener decenas de columnas de flags en la Fact Table.

📉 Degenerate Dimensions (Dimensiones Degeneradas)

Identificadores operacionales (como el numero_factura o ticket_id) que se almacenan directamente en la Fact Table sin tener una tabla de dimensión satélite asociada, porque todos sus atributos descriptivos ya pertenecen a otras dimensiones.

/* GUÍA MAESTRA DE SLOWLY CHANGING DIMENSIONS (SCD) */

SCD Tipo 1: Sobrescritura

Sobrescribe el valor anterior en el mismo registro. No guarda historial. Sencillo, pero destruye la trazabilidad histórica de reportes pasados.

SCD Tipo 2: Histórico con Filas

Crea una nueva fila con nueva Surrogate Key, marcando fecha_inicio, fecha_fin y flag es_actual. Estándar de oro en la industria.

SCD Tipo 3: Histórico en Columna

Agrega una columna adicional (ej. ciudad_anterior y ciudad_actual). Solo guarda el estado inmediatamente previo.

Cubos Multidimensionales y SQL Analítico (CUBE, ROLLUP)

Las operaciones canónicas sobre un Cubo OLAP permiten a los analistas de negocio explorar métricas desde distintas perspectivas jerárquicas:

  • Slice (Rebanar): Filtrar el cubo fijando una única dimensión (ej. ventas solo del año 2026).
  • Dice (Trocear): Subcubo definido por filtros en múltiples dimensiones (ej. ventas de 2026 en la Región Lima para la categoría Laptops).
  • Drill-down: Desglosar una métrica de un nivel jerárquico superior a uno más detallado (Año → Trimestre → Mes → Día).
  • Roll-up: Agregar datos subiendo en la jerarquía (Día → Mes → Año).
  • Pivot: Rotar los ejes dimensionales para visualización tabular cruzada.
SQL Analytics de Élite: Agregaciones Jerárquicas PostgreSQL 16/17 / Snowflake 
-- 1. ROLLUP: Subtotales jerárquicos (Año -> Mes -> Región)
SELECT 
    t.anio,
    t.mes,
    d.region,
    SUM(f.monto_neto_total) AS venta_total,
    GROUPING(t.anio, t.mes, d.region) AS nivel_agregacion
FROM fact_ventas f
JOIN dim_tiempo t ON f.fecha_sk = t.fecha_sk
JOIN dim_tienda d ON f.tienda_sk = d.tienda_sk
GROUP BY ROLLUP (t.anio, t.mes, d.region)
ORDER BY t.anio NULLS FIRST, t.mes NULLS FIRST;

-- 2. CUBE: Todas las 2^N combinaciones multidimensionales posibles
SELECT 
    p.categoria,
    d.canal,
    SUM(f.monto_neto_total) AS venta_total
FROM fact_ventas f
JOIN dim_producto p ON f.producto_sk = p.producto_sk
JOIN dim_tienda d ON f.tienda_sk = d.tienda_sk
GROUP BY CUBE (p.categoria, d.canal);

Principio de Kimball

Nunca unas tablas de hechos entre sí directamente (Fact to Fact JOIN). Realiza consultas a través de dimensiones conformadas o utiliza UNION ALL / Data Marts consolidados.
