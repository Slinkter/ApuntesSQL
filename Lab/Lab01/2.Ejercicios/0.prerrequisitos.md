## 1. Conceptos Base

### 1.1 ¿Qué es SQL?

**SQL (Structured Query Language)** es el lenguaje estándar universal para comunicarse con bases de datos relacionales. Nació en los años 70 en IBM bajo el nombre original de SEQUEL y hoy es soportado por prácticamente todos los sistemas de bases de datos del mundo.

> **Analogía:** Piensa en SQL como el **idioma inglés del mundo de las bases de datos**. Así como puedes usar inglés para comunicarte en un hotel en Japón, en un restaurante en Francia o en una conferencia en Alemania, puedes usar SQL para hablar con PostgreSQL en Perú, con MySQL en Brasil o con Oracle en Estados Unidos. Es el lenguaje común que todos entienden.

Con SQL puedes realizar 4 tipos de operaciones fundamentales:

| Operación | Subconjunto SQL | Comandos principales | Ejemplo en Northwind |
|-----------|----------------|---------------------|----------------------|
| **Definir estructuras** | DDL (Data Definition Language) | `CREATE`, `ALTER`, `DROP` | Crear la tabla `products` con sus columnas |
| **Manipular datos** | DML (Data Manipulation Language) | `INSERT`, `UPDATE`, `DELETE` | Insertar un nuevo producto en `products` |
| **Consultar datos** | DQL (Data Query Language) | `SELECT` | Consultar todos los productos con precio mayor a $30 |
| **Controlar acceso** | DCL (Data Control Language) | `GRANT`, `REVOKE` | Dar permisos de solo lectura a un usuario |

```sql
-- Ejemplo de cada subconjunto en acción:

-- DDL: Crear una tabla
CREATE TABLE audit_log (
    log_id SERIAL PRIMARY KEY,
    action TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- DML: Insertar un registro
INSERT INTO audit_log (action) VALUES ('Usuario conectado');

-- DQL: Consultar registros
SELECT * FROM audit_log WHERE action = 'Usuario conectado';

-- DCL: Dar permisos (requiere superusuario y rol existente)
CREATE ROLE report_user;
GRANT SELECT ON audit_log TO report_user;
```

#### SQL vs NoSQL: ¿Cuándo usar cada uno?

| Característica | SQL (Relacional) | NoSQL (No relacional) |
|----------------|------------------|----------------------|
| **Estructura** | Esquema fijo (tablas con columnas definidas) | Esquema flexible (documentos, grafos, clave-valor) |
| **Consistencia** | ACID — transacciones confiables | BASE — disponibilidad sobre consistencia |
| **Consultas** | Lenguaje estándar SQL | APIs propietarias por cada sistema |
| **Escalado** | Vertical (más CPU/RAM al servidor) | Horizontal (más servidores en red) |
| **Relaciones** | Excelentes (JOINs entre tablas) | Limitadas (duplicación de datos) |
| **Ejemplos** | PostgreSQL, MySQL, Oracle, SQL Server | MongoDB, Redis, Cassandra, Neo4j |
| **Cuándo usar** | Datos estructurados, integridad crítica, reportes complejos | Datos semi-estructurados, alta escritura, escalabilidad masiva |

> **Regla práctica en enterprise:** Si tus datos tienen relaciones claras (clientes → pedidos → productos) y necesitas integridad transaccional (banca, e-commerce, inventarios), usa SQL. Si necesitas escalabilidad masiva y tu esquema cambia frecuentemente (logs, IoT, redes sociales), considera NoSQL.

### 1.2 ¿Qué es PostgreSQL?

**PostgreSQL es un sistema de gestión de bases de datos relacional (RDBMS) de código abierto**, considerado el sucesor académico de la investigación original de Berkeley sobre bases de datos. Actualmente está en su versión 17 y es utilizado por empresas como Apple, Instagram, Spotify y el government de nhiều países.

> **Analogía:** Si los RDBMS fueran autos, PostgreSQL sería un **vehículo híbrido de última generación**: tiene la fiabilidad de un Toyota (cumplimiento ACID), la potencia de un BMW (funciones avanzadas como CTEs recursivas, JSONB, ventanas), y la personalización de un Tesla (extensibilidad total). MySQL, en comparación, sería un sedan confiable y rápido pero con menos features premium.

#### Características principales de PostgreSQL

| Característica | Qué significa | Por qué importa |
|----------------|---------------|-----------------|
| **ACID** | Atomicidad, Consistencia, Aislamiento, Durabilidad | Tus transacciones son confiables: si algo falla, todo se revierte. Sin pérdida de datos. |
| **SQL estándar avanzado** | Soporta CTEs, ventanas, JSONB, rangos, arrays | Puedes resolver problemas complejos en una sola consulta sin código adicional. |
| **MVCC** | Multi-Version Concurrency Control | Las lecturas nunca bloquean escrituras y viceversa. Ideal para sistemas multi-usuario. |
| **Extensibilidad** | Puedes crear tipos, operadores, funciones e índices personalizados | Si PostgreSQL no tiene lo que necesitas, lo creas tú mismo. |
| **JSONB nativo** | Almacena y consulta JSON de forma binaria y eficiente | Puedes usar PostgreSQL como base de datos relacional Y como NoSQL en uno solo. |
| **GPL/Open Source** | Licencia gratuita, sin costos de usuario | Cero costo de licenciamiento, ideal para startups y enterprise. |

#### MySQL vs PostgreSQL: Comparación para profesionales

| Aspecto | MySQL | PostgreSQL |
|---------|-------|------------|
| **Licencia** | GPL (Oracle) | PostgreSQL License (más permisiva) |
| **ACID completo** | Solo con InnoDB (motor por defecto) | Siempre, en todos los motores |
| **Tipos de dato** | Básicos (INT, VARCHAR, TEXT) | Avanzados (JSONB, arrays, rangos, hstore, geometric) |
| **CTEs** | Soporte básico (8.0+) | Soporte completo + recursivos + MATERIALIZED/NOT MATERIALIZED |
| **Ventanas (WINDOW)** | Soporte parcial (8.0+) | Soporte completo y optimizado |
| **FULL OUTER JOIN** | No soportado | Soportado |
| **UPSERT** | `INSERT ... ON DUPLICATE KEY UPDATE` | `INSERT ... ON CONFLICT DO UPDATE` (más expresivo) |
| **RETURNING** | No soportado (necesitas 2 queries) | Soportado — devuelve datos de la fila afectada |
| **Particionamiento** | Limitado (MySQL 8.0+) | Nativo y declarativo (desde PostgreSQL 10) |
| **MVCC** | Implementación parcial | Completo — lecturas nunca bloquean escrituras |
| **Extensibilidad** | Plugins limitados | Extensiones completas (PostGIS, pg_trgm, pgvector) |
| **Escritura** | Más rápido en carga simple | Más lento en carga masiva, más rápido en consultas complejas |
| **Comunidad** | Oracle (empresa privada) | Comunidad open source global |

> **Cuándo elegir PostgreSQL en un proyecto enterprise:**
> - Necesitas integridad transaccional completa (banca, pagos)
> - Trabajas con datos geoespaciales (PostGIS es el estándar de la industria)
> - Necesitas JSONB para datos semi-estructurados sin cambiar de base de datos
> - Tu equipo值a la estabilidad y estándares SQL sobre la velocidad de escritura bruta
> - Estás en cloud: AWS RDS, Google Cloud SQL y Azure Database soportan PostgreSQL nativamente

### 1.3 Modelo Relacional

El **modelo relacional** es la forma de organizar datos en tablas (llamadas "relaciones") donde cada fila representa una entidad y cada columna una propiedad de esa entidad. Fue inventado por Edgar F. Codd en 1970 y sigue siendo la base de casi todas las bases de datos del mundo empresarial.

> **Analogía:** Imagina una hoja de cálculo de Excel, pero con reglas estrictas:
> - Cada columna tiene un tipo de dato definido (no puedes poner texto en una columna de fechas)
> - Cada fila es única (no puedes tener dos clientes con el mismo ID)
> - Las celdas están relacionadas entre hojas (el pedido de un cliente apunta a ese cliente específico)
> - Las reglas se enforced automáticamente por la base de datos (si intentas borrar un cliente con pedidos, PostgreSQL te lo impide)

#### Componentes fundamentales

| Componente | Definición | Ejemplo en Northwind |
|------------|-----------|----------------------|
| **Tabla (Relación)** | Conjunto de filas con la misma estructura | `customers`, `orders`, `products` |
| **Fila (Tupla/Registro)** | Una instancia de la entidad | El cliente "ALFKI" de Alfreds Futterkiste |
| **Columna (Atributo)** | Una propiedad de la entidad | `company_name`, `order_date`, `unit_price` |
| **Clave Primaria (PK)** | Columna o combinación que identifica **de forma única** cada fila | `customer_id` en `customers`, `(order_id, product_id)` en `order_details` |
| **Clave Foránea (FK)** | Columna que referencia la PK de otra tabla, creando una relación | `orders.customer_id` → `customers.customer_id` |

#### Ejemplo con datos reales de Northwind

```
 customers                     orders                    order_details
┌──────────────┐          ┌─────────────────┐        ┌───────────────────────┐
│ customer_id  │          │ order_id (PK)   │        │ order_id (PK, FK)     │
│ company_name │          │ customer_id(FK) │        │ product_id (PK, FK)   │
│ contact_name │          │ order_date      │        │ unit_price            │
│ country      │          │ ship_country    │        │ quantity              │
└──────┬───────┘          └────────┬────────┘        └───────────┬───────────┘
       │                           │                             │
       │   ┌───────────────────────┘                             │
       │   │                                                     │
       └───┤ orders.customer_id = customers.customer_id          │
           │                                                     │
           └──────────────── order_details.order_id = orders.order_id
                                                       │
                                         order_details.product_id = products.product_id
```

```sql
-- Consulta que demuestra las 3 tablas relacionadas
SELECT
    c.company_name,          -- de customers
    o.order_date,            -- de orders
    p.product_name,          -- de products
    od.quantity,             -- de order_details
    od.unit_price            -- de order_details
FROM order_details od
JOIN orders o     ON od.order_id = o.order_id
JOIN customers c  ON o.customer_id = c.customer_id
JOIN products p   ON od.product_id = p.product_id
LIMIT 5;
```

#### Patrones de relación en bases de datos reales

| Patrones | Qué es | Ejemplo en Northwind | Diagrama |
|----------|--------|----------------------|----------|
| **1:N (Uno a Muchos)** | Una fila de A se relaciona con muchas filas de B | Un cliente tiene muchos pedidos | `customers (1) ──< (N) orders` |
| **N:N (Muchos a Muchos)** | Muchas filas de A se relacionan con muchas filas de B, vía tabla puente | Un pedido tiene muchos productos, un producto está en muchos pedidos | `orders ──< order_details >── products` |
| **Autorreferencial** | Una tabla se relaciona consigo misma | Un empleado reporta a otro empleado | `employees ──< employees` (via `reports_to`) |

```sql
-- Ejemplo de relación autorreferencial: jerarquía de empleados
SELECT
    e.first_name || ' ' || e.last_name AS empleado,
    COALESCE(m.first_name || ' ' || m.last_name, '(CEO)') AS reporta_a
FROM employees e
LEFT JOIN employees m ON e.reports_to = m.employee_id
ORDER BY e.reports_to;
```

### 1.4 Fundamentos de Teoría Relacional: Lógica Trivalente (3VL) y Pensamiento en Conjuntos

> **Tratados de Referencia:**  
> - Edgar F. Codd (1970, 1990): *A Relational Model of Data for Large Shared Data Banks*.  
> - C.J. Date (2011): *SQL and Relational Theory: How to Write Accurate SQL Code* (Capítulos 3, 4 y 6).  
> - Joe Celko (2008): *Thinking in Sets: Auxiliary, Temporal, and Virtual Tables in SQL* (Capítulos 1 y 2).

#### 1.4.1 El Principio de "All-at-Once Operations" (Joe Celko)
En los lenguajes de programación imperativos (Python, Java, C++), las instrucciones se evalúan línea por línea, de arriba hacia abajo y de izquierda a derecha. En contraste, **SQL es un lenguaje declarativo orientado a conjuntos**.

Según el principio formal de **Operaciones All-at-Once** formulado por Joe Celko:
- Todas las expresiones dentro de una misma cláusula (`SELECT`, `WHERE`, `SET`) se evalúan **conceptualmente de forma simultánea e instantánea**.
- **Consecuencia Matemática:** Una columna calculada en la cláusula `SELECT` no puede ser utilizada inmediatamente por otra expresión en la misma cláusula `SELECT`, ni tampoco en la cláusula `WHERE` de la misma consulta, porque todo el conjunto se proyecta en un único paso lógico.

```sql
-- ❌ ERROR COMÚN (Mentalidad Procedural): Intentar usar un alias en el mismo nivel
SELECT 
    unit_price * quantity AS subtotal,
    subtotal * (1 - discount) AS total_neto  -- ¡ERROR: "subtotal" no existe en este paso!
FROM order_details;

-- ✅ FORMA CORRECTA (Mentalidad de Conjuntos): Repetir la expresión o encapsular en CTE / Subquery
SELECT 
    subtotal,
    subtotal * (1 - discount) AS total_neto
FROM (
    SELECT unit_price * quantity AS subtotal, discount
    FROM order_details
) t;
```

#### 1.4.2 Lógica Trivalente (3VL: TRUE, FALSE, UNKNOWN) y Semántica de NULLs
En el modelo relacional puro y en el estándar ISO/IEC SQL, `NULL` **no es un valor**, sino un marcador que representa la **ausencia de valor** o información desconocida. En consecuencia, cualquier comparación con `NULL` no puede evaluarse a `TRUE` ni a `FALSE`, sino a un tercer valor de verdad: **`UNKNOWN`**.

##### Tablas de Verdad en Lógica Trivalente (3VL)

| $A$ | $B$ | $A \land B$ (AND) | $A \lor B$ (OR) | $\neg A$ (NOT) |
| :---: | :---: | :---: | :---: | :---: |
| **TRUE** | **TRUE** | **TRUE** | **TRUE** | **FALSE** |
| **TRUE** | **FALSE** | **FALSE** | **TRUE** | **FALSE** |
| **TRUE** | **UNKNOWN** | **UNKNOWN** | **TRUE** | **FALSE** |
| **FALSE** | **FALSE** | **FALSE** | **FALSE** | **TRUE** |
| **FALSE** | **UNKNOWN** | **FALSE** | **UNKNOWN** | **TRUE** |
| **UNKNOWN** | **UNKNOWN** | **UNKNOWN** | **UNKNOWN** | **UNKNOWN** |

##### Divergencia Semántica de Aceptación de UNKNOWN en PostgreSQL

| Contexto SQL | Criterio de Aceptación | ¿Pasa el filtro si la condición es `UNKNOWN`? |
| :--- | :--- | :---: |
| **`WHERE` / `HAVING` / `ON`** | Aceptación estricta de Verdad ($\text{Condición} = \text{TRUE}$) | ❌ **Rechazado** (Descarta `FALSE` y `UNKNOWN`) |
| **`CHECK Constraints`** | Rechazo estricto de Falsedad ($\text{Condición} \neq \text{FALSE}$) | ✅ **Aceptado** (Permite `TRUE` y `UNKNOWN`) |
| **`UNIQUE Constraints`** | En SQL estándar y PG (<15), `NULL != NULL` es `UNKNOWN` | ✅ **Aceptado** (Permite múltiples tuplas con `NULL`) |

#### 1.4.3 La Trampa Matemática de `NOT IN` con Subconsultas que contienen NULLs

Uno de los errores más graves en producción ocurre al utilizar el predicado `NOT IN` contra una subconsulta que devuelve al menos una fila con `NULL`.

##### Demostración Formal:
Supongamos que deseamos encontrar clientes que **no** han emitido pedidos:
```sql
-- ⚠️ TRAMPA CRÍTICA: Si la subconsulta contiene un solo NULL, devuelve 0 filas
SELECT customer_id, company_name
FROM customers
WHERE customer_id NOT IN (
    SELECT customer_id FROM orders -- Si hay un pedido con customer_id NULL
);
```

**Desglose algebraico:**
1. La expresión `x NOT IN (val1, val2, NULL)` se expande por equivalencia de De Morgan a:
   $$x \neq \text{val1} \land x \neq \text{val2} \land x \neq \text{NULL}$$
2. Como cualquier comparación con `NULL` evalúa a `UNKNOWN`:
   $$x \neq \text{NULL} \implies \text{UNKNOWN}$$
3. Sustituyendo en la conjunción booleana:
   $$\text{TRUE} \land \text{TRUE} \land \text{UNKNOWN} \implies \text{UNKNOWN}$$
4. Dado que la cláusula `WHERE` solo acepta filas que evalúen estrictamente a **`TRUE`**, **la consulta descarta absolutamente todas las filas y devuelve un conjunto vacío ($\emptyset$)**.

##### Soluciones Robustas de Ingeniería:
```sql
-- Opción 1: Anti-Join con NOT EXISTS (Short-Circuit Seguro)
SELECT c.customer_id, c.company_name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);

-- Opción 2: LEFT JOIN con IS NULL
SELECT c.customer_id, c.company_name
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;
```

### 1.5 Índices

**Un índice es una estructura de datos auxiliar que acelera significativamente la búsqueda de filas** en una tabla. Sin un índice, PostgreSQL debe leer toda la tabla fila por fila (escaneo secuencial). Con un índice, salta directamente a las filas que necesitas.

> **Analogía (mejorada):** Imagina que necesitas encontrar "el capítulo sobre transacciones" en un libro de 500 páginas:
> - **Sin índice:** Abres el libro en la página 1 y lees cada página hasta encontrar la palabra "transacciones". Si el libro tiene 500 páginas, podrías necesitar leer 400 páginas antes de encontrarlo. → **Esto es un Seq Scan.**
> - **Con índice:** Miras el índice alfabético al final del libro. Dice "transacciones — página 347". Abres directamente en la página 347. → **Esto es un Index Scan.**
> - **Con un índice compuesto (como un índice temático):** Si buscas "transacciones en PostgreSQL", el índice te dice primero "PostgreSQL (páginas 100-200)" y luego "transacciones (página 156)". → **Esto es un Index Scan con predicado de columna.**

#### Tipos de índices en PostgreSQL

| Tipo de índice | Cuándo usarlo | Ejemplo | Rendimiento |
|----------------|---------------|---------|-------------|
| **B-tree** (default) | Columnas con valores ordenables (=, <, >, BETWEEN, IS NULL) | `CREATE INDEX idx ON orders(order_date)` | Rápido para búsquedas de rango y igualdad |
| **Hash** | Solo igualdad exacta (=) | `CREATE INDEX idx ON customers USING hash(customer_id)` | Más rápido que B-tree para igualdad pura, pero no soporta rangos |
| **GiST** | Datos geoespaciales, Full-Text Search, rangos, arrays | `CREATE INDEX idx ON locations USING gist(geom)` | Esencial para PostGIS y búsqueda textual |
| **GIN** | Arrays, JSONB, Full-Text Search | `CREATE INDEX idx ON products USING gin(search_vector)` | Rápido para contiene (@>) y coincidencia textual |
| **BRIN** | Tablas muy grandes con datos naturalmente ordenados (timestamps, secuencias) | `CREATE INDEX idx ON logs USING brin(created_at)` | Muy pequeño, ideal para tablas de billones de filas |

```sql
-- Ejemplo práctico: crear un índice y verificar su uso
-- Paso 1: Crear índice en la columna de búsqueda
CREATE INDEX idx_orders_customer ON orders(customer_id);

-- Paso 2: Verificar que PostgreSQL lo usa
EXPLAIN SELECT * FROM orders WHERE customer_id = 'ALFKI';

-- Output esperado:
-- Index Scan using idx_orders_customer on orders
--   Index Cond: (customer_id = 'ALFKI'::character(5))

-- Paso 3: Comparar con y sin índice
-- Sin índice: Seq Scan (lee las 830 filas)
-- Con índice: Index Scan (salta directamente a las filas de ALFKI)
```

#### ¿Cuándo crear un índice?

| Señal | Acción recomendada |
|-------|-------------------|
| `Seq Scan` en tabla > 10,000 filas en un `WHERE` frecuente | Crear índice en la columna del `WHERE` |
| `Seq Scan` en un `JOIN` frecuente | Crear índice en la columna de JOIN (FK) |
| Consultas `ORDER BY` lentas | Crear índice en la columna de ordenamiento |
| Tabla con muchos `NULL` y consultas que filtran por `IS NOT NULL` | Considerar índice parcial: `CREATE INDEX idx ON t(col) WHERE col IS NOT NULL` |
| Tabla pequeña (< 1,000 filas) | Generalmente NO necesita índice (el Seq Scan es suficiente) |

### 1.6 SET search_path

```sql
SET search_path TO public;
```

**`search_path` es el directorio de búsqueda de PostgreSQL.** Cuando escribes `SELECT * FROM customers`, PostgreSQL busca la tabla `customers` en cada schema listado en `search_path`, en orden. Por defecto busca en `public`.

> **Analogía:** Es como la variable `PATH` en tu terminal. Cuando escribes `python` en la terminal, el sistema busca en `/usr/bin`, `/usr/local/bin`, etc. Hasta encontrar el ejecutable. PostgreSQL hace lo mismo con los schemas.

```sql
-- Ver el search_path actual
SHOW search_path;

-- Resultado por defecto: "$user", public
-- PostgreSQL primero busca en un schema con tu nombre de usuario,
-- luego en "public"

-- En este laboratorio siempre estamos en "public"
SET search_path TO public;
```

> **En enterprise:** En producción, normalmente tienes múltiples schemas: `public` (datos de la aplicación), `audit` (logs de cambios), `reporting` (vistas materializadas). El `search_path` controla a cuál accedes por defecto.

## 2. Setup del Laboratorio (Docker & AWS EC2)

> **Analogía del laboratorio virtual:** Docker es como un **laboratorio de química completamente equipado** que puedes encender y apagar con un botón. En lugar de instalar PostgreSQL directamente en tu computadora (como si construyeras un laboratorio propio), Docker te da un contenedor aislado con todo listo. ### 2.1 ¿Por qué Docker en vez de instalación nativa?

| Aspecto | Instalación nativa | Docker |
|---------|-------------------|--------|
| **Setup** | Descargar, instalar, configurar, crear BD | Un solo comando |
| **Aislamiento** | Se instala en tu sistema, puede conflictuar con otras versiones | Contenedor completamente aislado |
| **Cleanup** | Desinstalar manualmente, limpiar archivos residuales | `docker rm` — limpio en 1 segundo |
| **Portabilidad** | Funciona solo en tu máquina | Funciona igual en Windows, Mac, Linux, CI/CD |
| **Múltiples versiones** | Difícil (PostgreSQL 14 y 16 en la misma máquina) | Fácil (cada contenedor con su versión) |
| **Reproducibilidad** | "Funciona en mi máquina" | "Funciona en cualquier máquina con Docker" |

### 2.2 Requisitos de Software

### 4.2 Patrones de Relación en Northwind

Northwind demuestra los 3 patrones fundamentales de diseño relacional:

#### Patrón 1: Uno a Muchos (1:N)

```
categories (1) ──< (N) products
Un categoría tiene muchos productos, un producto pertenece a una categoría.

customers (1) ──< (N) orders
Un cliente hace muchos pedidos, un pedido pertenece a un solo cliente.

employees (1) ──< (N) orders
Un empleado gestiona muchos pedidos, un pedido es gestionado por un empleado.
```

```sql
-- Ejemplo: ver cuántos productos tiene cada categoría
SELECT
    c.category_name,
    COUNT(p.product_id) AS total_productos
FROM categories c
LEFT JOIN products p ON c.category_id = p.category_id
GROUP BY c.category_name
ORDER BY total_productos DESC;
```

#### Patrón 2: Muchos a Muchos (N:N) vía tabla puente

```
orders (N) ──< order_details >── (N) products
Un pedido tiene muchos productos, un producto está en muchos pedidos.
La tabla "order_details" es la tabla puente (junction table) que resuelve la relación N:N.
```

> **Por qué no se puede hacer N:N directamente:** En el modelo relacional, una FK apunta a una sola fila de otra tabla. Si un pedido tiene 10 productos, ¿a cuál apuntaría `orders.product_id`? La solución es crear una tabla intermedia (`order_details`) donde cada fila es una combinación (pedido, producto) con su cantidad y precio.

```sql
-- Ejemplo: ver el detalle de un pedido específico
SELECT
    p.product_name,
    od.quantity,
    od.unit_price,
    od.discount,
    (od.quantity * od.unit_price * (1 - od.discount)) AS total_linea
FROM order_details od
JOIN products p ON od.product_id = p.product_id
WHERE od.order_id = 10248;
```

#### Patrón 3: Autorreferencial (Self-referencing)

```
employees (1) ──< (N) employees
Un empleado reporta a otro empleado (jerarquía organizacional).
La FK "reports_to" apunta a "employee_id" de la misma tabla.
```

```sql
-- Ejemplo: ver la jerarquía de empleados
SELECT
    e.first_name || ' ' || e.last_name AS empleado,
    e.title AS cargo,
    COALESCE(m.first_name || ' ' || m.last_name, '(CEO / Sin jefe)') AS reporta_a
FROM employees e
LEFT JOIN employees m ON e.reports_to = m.employee_id
ORDER BY e.reports_to NULLS FIRST;
```

### 4.3 Tipos de Datos PostgreSQL en Northwind

| Tipo PostgreSQL | Tamaño | Equivalente | Uso en Northwind | Cuándo usarlo |
|-----------------|--------|-------------|------------------|---------------|
| `smallint` | 2 bytes | INT2 | `category_id`, `supplier_id`, `quantity` | Enteros pequeños (IDs, cantidades, stocks) |
| `integer` | 4 bytes | INT4 | `discontinued` | Enteros estándar |
| `numeric` | Variable | DECIMAL | `unit_price`, `freight`, `discount` | Dinero, porcentajes — **nunca usa `float` para dinero** |
| `varchar(n)` | Variable | STRING | `company_name`, `contact_name` | Texto con longitud máxima conocida |
| `text` | Variable | TEXT | `description`, `notes` | Texto libre sin límite de longitud |
| `date` | 4 bytes | DATE | `order_date`, `birth_date` | Solo fecha (sin hora) |
| `bytea` | Variable | BLOB | `picture`, `photo` | Datos binarios (imágenes, archivos) |

> **Analogía `numeric` vs `float`:** ¿Preferirías que tu banco de alimentos usara `float` para calcular tus pagos? Un `float` es como un cálculo con regla de tres: rápido pero impreciso (`0.1 + 0.2 = 0.30000000000000004`). Un `numeric` es como una calculadora de contabilidad: exacto (`0.1 + 0.2 = 0.3`). Para dinero, SIEMPRE usa `numeric`.

### 4.4 Convención de Columnas

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `unit_price` | `numeric` | Precio sin pérdida de precisión |
| `quantity` | `integer` | Cantidad de ítems |
| `discount` | `numeric` | Descuento en porcentaje (0.00 a 0.25) |
| `customer_id` | `character(5)` | Siempre 5 caracteres, PK de customers |
| `order_date` | `date` | Fecha del pedido (sin hora) |

### 4.5 Diseño de Constraints

| Constraint | Tipo | Ejemplo en Northwind | Propósito |
|------------|------|----------------------|-----------|
| **PRIMARY KEY** | `pk_orders` | `order_id` en `orders` | Garantiza unicidad — no puede haber dos pedidos con el mismo ID |
| **FOREIGN KEY** | `fk_orders_customers` | `customer_id` en `orders` → `customers` | Integridad referencial — no puede existir un pedido de un cliente inexistente |
| **NOT NULL** | Implícito en PKs | Todas las PKs | No permite valores nulos en la columna identificadora |
| **UNIQUE** | No definido en Northwind | — | Northwind no usa UNIQUE (en producción sería útil en `email`, `phone`) |
| **CHECK** | No definido en Northwind | — | Northwind no usa CHECK (en producción: `CHECK (unit_price > 0)`) |

> **Nota sobre Northwind:** El esquema original no incluye constraints `CHECK` ni `UNIQUE`. En un sistema de producción, agregarías validaciones como `CHECK (quantity > 0)`, `CHECK (discount >= 0 AND discount <= 1)`, o `UNIQUE (email)` en la tabla de usuarios.

## 5. Cómo Leer y Optimizar EXPLAIN (ANALYZE, BUFFERS)

**`EXPLAIN` es el GPS de tus consultas SQL.** Antes de ejecutar una ruta, un GPS te muestra el camino óptimo: "toma la autopista, luego gira a la derecha, evita el tráfico del centro". PostgreSQL hace exactamente lo mismo con tus consultas: analiza la tabla, estima costos, elige el mejor camino y te muestra el plan de ejecución.

> **Analogía completa:** Imagina que necesitas ir del aeropuerto de Lima al centro de la ciudad:
> - **Sin EXPLAIN:** Tomas el primer camino que ves y esperas que sea el más rápido (puedes terminar en El Rospo).
> - **Con EXPLAIN:** El GPS te dice: "Hay 3 rutas. La ruta A toma 25 min (autopista, 15km), la ruta B toma 40 min (vía expresa, 12km), la ruta C toma 60 min (callejera, 8km). Te recomiendo la ruta A."
> - **Con EXPLAIN ANALYZE:** El GPS te dice lo mismo, pero además te dice: "Tardé exactamente 23 minutos y recorrí 14.8km." (datos reales, no estimados).

### 5.1 Sintaxis

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers WHERE country = 'Mexico';
```

| Flag | Qué hace | Cuándo usarlo |
|------|----------|---------------|
| `EXPLAIN` solo | Muestra el plan **estimado** (sin ejecutar) | Para ver qué hará PostgreSQL sin gastar recursos |
| `EXPLAIN ANALYZE` | **Ejecuta** la query y muestra tiempos reales | Para medir performance real |
| `EXPLAIN ANALYZE, BUFFERS` | Agrega información de **E/S de disco** | Para diagnosticar problemas de I/O |
| `EXPLAIN ANALYZE, BUFFERS, FORMAT JSON` | Salida en JSON para análisis programático | Para integrar con herramientas de monitoreo |

### 5.2 Ejemplo completo

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.company_name, COUNT(o.order_id) AS pedidos
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE c.country = 'Mexico'
GROUP BY c.company_name;
```

### 5.3 Cómo pensar como el optimizador

Cuando PostgreSQL recibe una consulta, sigue estos pasos internos (que EXPLAIN te muestra):

| Paso | Qué hace PostgreSQL | Pregunta que se responde |
|------|---------------------|--------------------------|
| **1. Analiza tablas** | ¿Qué tablas necesito? ¿Cuántas filas tiene cada una? | `Seq Scan on customers c` |
| **2. Estima cardinalidad** | ¿Cuántas filas cree que coincidirán con el `WHERE`? | `rows=5` (estima 5 clientes en México) |
| **3. Elige algoritmo de JOIN** | ¿Hash Join, Nested Loop o Merge Join? | `Hash Right Join` |
| **4. Estima costos** | ¿Cuánto cuesta cada operación? (lectura de disco, CPU, memoria) | `cost=... rows=... width=...` |
| **5. Ejecuta el plan** | Sigue el árbol de nodos de abajo hacia arriba | `actual time=0.45..0.47` |

### 5.4 Interpretación de cada elemento

| Elemento | Significa | Qué mirar |
|----------|-----------|-----------|
| `Seq Scan` | Escaneo secuencial (lee toda la tabla) | Normal en tablas pequeñas,Problemático en tablas grandes |
| `Index Scan` | Escaneo por índice (salta a filas específicas) | Lo que quieres ver en consultas WHERE |
| `Hash Join` | Construye hash de una tabla y escanea la otra | Óptimo para JOINs sin índice en la columna de unión |
| `Nested Loop` | Para cada fila de A, busca en B | Óptimo para conjuntos pequeños o con índice |
| `Merge Join` | Ordena ambas tablas y las fusiona | Óptimo para datos preordenados o con índice |
| `cost=...` | Costo estimado (unidad arbitraria, comparativo) | No es tiempo real — es una estimación |
| `actual time=0.45..0.47` | Tiempo real en ms (inicio..fin del nodo) | El tiempo real de ejecución de ese nodo |
| `rows=5` | Filas reales producidas por ese nodo | Si difiere mucho del estimado → estadísticas desactualizadas |
| `loops=1` | Veces que se ejecutó este nodo | En Nested Loop, puede ser alto |
| `Buffers: shared hit=16` | 16 bloques leídos desde caché de memoria | Rápido — datos en RAM |
| `Buffers: shared read=10` | 10 bloques leídos desde disco | Lento — posible bottleneck de I/O |
| `Planning Time` | Tiempo que el optimizador tardó en elegir el plan | Si es alto, la query tiene muchas tablas o complejidad |
| `Execution Time` | Tiempo total de ejecución | El número que más te importa para performance |

### 5.5 Ejemplo práctico: antes/después de crear un índice

```sql
-- ANTES del índice: Seq Scan en 830 filas
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 'ALFKI';
-- Seq Scan on orders  (cost=0.00..22.30 rows=1 width=...)
--   Filter: (customer_id = 'ALFKI'::character(5))
--   Rows Removed by Filter: 829
-- Execution Time: 0.15 ms  (pero lee TODA la tabla)

-- Crear el índice
CREATE INDEX idx_orders_customer ON orders(customer_id);

-- DESPUÉS del índice: Index Scan directo
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 'ALFKI';
-- Index Scan using idx_orders_customer on orders
--   Index Cond: (customer_id = 'ALFKI'::character(5))
-- Execution Time: 0.05 ms  (salta directamente a la fila)
```

### 5.6 Señales de alarma en EXPLAIN

| Señal | Significado | Solución |
|-------|-------------|----------|
| `Seq Scan` en tabla > 10,000 filas | PostgreSQL lee toda la tabla | Crear índice en la columna del `WHERE` |
| `Buffers: shared read` alto | Muchas lecturas de disco | Aumentar `shared_buffers` o crear índices |
| Diferencia grande entre `rows` estimado y real | Estadísticas desactualizadas | Ejecutar `ANALYZE nombre_tabla` |
| `Sort Method: external merge Disk` | Sorting usingando disco (lento) | Aumentar `work_mem` o crear índice en la columna de `ORDER BY` |
| `Nested Loop` con `loops=1000` | Muchas iteraciones | Considerar un `Hash Join` o índice compuesto |

Un índice no es simplemente una estructura estática. En entornos de alta concurrencia, la elección del tipo de índice y su definición determinan el rendimiento global del cluster:

```sql
-- 1. Índice Compuesto con Orden Específico (Multi-column)
CREATE INDEX idx_orders_user_date ON orders(customer_id, order_date DESC);

-- 2. Índice Parcial (Partial Index) - Reduce el tamaño del índice en un 80%
CREATE INDEX idx_orders_unshipped ON orders(order_id) 
WHERE shipped_date IS NULL;

-- 3. Índice Expresional (Expression / Functional Index)
CREATE INDEX idx_customers_lower_company ON customers(lower(company_name));

-- 4. Índice Cubriente (Covering Index con cláusula INCLUDE) - Habilita Index Only Scan
CREATE INDEX idx_orders_covering ON orders(customer_id) 
INCLUDE (order_date, freight);

-- 5. Índice GIN para datos JSONB o Full-Text Search
-- CREATE INDEX idx_events_data_gin ON events USING gin(data);
```

### 6.1 Observabilidad y Detección de Cuellos de Botella con `pg_stat_statements`

Para identificar consultas lentas y consumo de I/O en producción:

```sql
-- Identificar el TOP 10 de consultas más lentas y su tasa de acierto en memoria caché
SELECT 
    query, 
    calls, 
    round(total_exec_time::numeric, 2) AS total_time_ms, 
    round(mean_exec_time::numeric, 2) AS mean_time_ms, 
    rows,
    round((100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0))::numeric, 2) AS hit_percent
FROM pg_stat_statements 
ORDER BY total_exec_time DESC 
LIMIT 10;
```

## 7. Transacciones: ACID y Niveles de Aislamiento

**Una transacción es una unidad atómica de trabajo: o se ejecutan TODAS las operaciones dentro de ella, o no se ejecuta NINGUNA.** Es el mecanismo fundamental que garantiza la integridad de datos en sistemas de producción.

> **Analogía del punto de restauración:** Imagina que estás jugando un videojuego con sistema de guardado:
> - **BEGIN** = Creas un punto de guardado nuevo
> - **INSERT/UPDATE/DELETE** = Avanzas en el juego (matas monstruos, recoges tesoros)
> - **COMMIT** = Guardas el juego permanentemente (los cambios son irreversibles)
> - **ROLLBACK** = Cargas el punto de guardado anterior (todo vuelve al estado anterior, como si no hubieras hecho nada)

### 7.1 Flujo Básico Transaccional

```sql
-- Iniciar transacción (crea un punto de guardado)
BEGIN;

-- Se utiliza un ID válido dentro del rango smallint (max 32767)
INSERT INTO orders (order_id, customer_id, employee_id, order_date)
VALUES (20000, 'ALFKI', 1, CURRENT_DATE);

UPDATE customers
SET contact_name = 'Nuevo Contacto'
WHERE customer_id = 'ALFKI';

-- Confirmar cambios (punto de guardado permanente)
COMMIT;
```

### 7.2 Rollback (Deshacer Operaciones)

```sql
BEGIN;
DELETE FROM orders WHERE order_id = 20000;
-- Se detecta una condición errónea y se revierte
ROLLBACK;  -- Todo vuelve al estado anterior, como si el DELETE nunca hubiera existido
```

### 7.3 Transacciones Anidadas con SAVEPOINT

```sql
BEGIN;
  INSERT INTO customers (customer_id, company_name) VALUES ('TEST1', 'Test Corp');
  SAVEPOINT sp1;               -- Creamos un sub-punto de guardado
  INSERT INTO orders (order_id, customer_id) VALUES (20001, 'TEST1'); -- Supongamos que esto falla
  ROLLBACK TO SAVEPOINT sp1;   -- Deshace solo el INSERT de orders
  -- El registro de customers insertado se conserva
COMMIT;
```

> **En producción:** Los `SAVEPOINT` son útiles cuando una transacción grande puede fallar parcialmente. Por ejemplo, al importar 1000 registros, si el registro 500 falla, puedes hacer `ROLLBACK TO SAVEPOINT` antes del 500 y continuar con el resto sin abortar todo el lote.

### 7.4 Niveles de Aislamiento y Anomalías de Concurrencia

| Nivel de Aislamiento | Dirty Read | Non-Repeatable Read | Phantom Read | Serialization Anomaly | Comportamiento en PostgreSQL |
|---|:---:|:---:|:---:|:---:|---|
| **Read Uncommitted** | ❌ Prevenido | ⚠️ Posible | ⚠️ Posible | ⚠️ Posible | Tratado internamente como *Read Committed* debido a MVCC. |
| **Read Committed** | ❌ Prevenido | ⚠️ Posible | ⚠️ Posible | ⚠️ Posible | **Por defecto en PostgreSQL.** Cada sentencia ve un snapshot al inicio de la query. |
| **Repeatable Read** | ❌ Prevenido | ❌ Prevenido | ❌ Prevenido (en PG) | ⚠️ Posible (*Write Skew*) | La transacción ve un snapshot fijo tomado al inicio de la primera query. |
| **Serializable (SSI)**| ❌ Prevenido | ❌ Prevenido | ❌ Prevenido | ❌ Prevenido | Aislamiento estricto equivalente a ejecución puramente secuencial. |

```sql
-- Ejemplo: cambiar nivel de aislamiento a Repeatable Read
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM orders WHERE customer_id = 'ALFKI';  -- Snapshot inicial
-- Otro usuario inserta y confirma un pedido de ALFKI concurrentemente
SELECT COUNT(*) FROM orders WHERE customer_id = 'ALFKI';  -- Sigue viendo el mismo valor del snapshot
COMMIT;
```

### 7.5 Race Conditions y Bloqueo Pesimista (FOR UPDATE)

```sql
-- SIN transacción / control de concurrencia (Peligroso):
-- Usuario A: Lee stock = 10
-- Usuario B: Lee stock = 10
-- Usuario A: UPDATE stock = 10 - 3 = 7
-- Usuario B: UPDATE stock = 10 - 5 = 5  ← ¡Sobrescribió el cambio de A! (Lost Update)

-- CON Bloqueo Pesimista explícito (Seguro para alta concurrencia):
BEGIN;
SELECT units_in_stock 
FROM products 
WHERE product_id = 1 
FOR UPDATE; -- Bloquea la tupla a nivel de fila hasta el COMMIT

UPDATE products 
SET units_in_stock = units_in_stock - 3 
WHERE product_id = 1;

COMMIT;
```

### 7.6 Buenas Prácticas de Ingeniería Transaccional

| Práctica | Por qué importa |
|----------|-----------------|
| **Transacciones cortas y atómicas** | Minimizan el tiempo de retención de bloqueos y reducen contención en el Buffer Pool |
| **Siempre COMMIT o ROLLBACK explícito** | Evita fugas de conexiones y transacciones huérfanas en estado `idle in transaction` |
| **DML destructivo validado con EXPLAIN** | `BEGIN; EXPLAIN ANALYZE <DML>; ROLLBACK;` para auditar impacto antes de aplicar |
| **SAVEPOINTs delimitados en cargas batch** | Permite recuperación de errores a nivel de registro sin descartar el lote completo |

```sql
-- Patrón seguro para DML destructivo en producción
BEGIN;
EXPLAIN ANALYZE
DELETE FROM orders WHERE order_date < '1990-01-01';
-- Veo que borraría 0 filas (la fecha más antigua es 1996)
ROLLBACK;  -- no ejecuto el DELETE, solo quería ver el impacto
```

### 8.2 MVCC, Bloat, Autovacuum y Visibility Map

En PostgreSQL, la concurrencia se implementa mediante **MVCC (Multi-Version Concurrency Control)**. Esto significa que **las lecturas nunca bloquean a las escrituras, y las escrituras nunca bloquean a las lecturas**.

#### Estructura Interna de una Tupla en el Heap
Cada fila física (tupla) en una página de 8KB contiene una cabecera oculta con metadatos de control transaccional:
- **`xmin` (4 bytes):** ID de la transacción que insertó la tupla.
- **`xmax` (4 bytes):** ID de la transacción que borró o actualizó la tupla (0 si está viva y activa).
- **`ctid` (6 bytes):** Puntero físico `(número_de_página, índice_de_línea)` a la ubicación física de la tupla o su versión más reciente.
- **`infomask` (2 bytes):** Banderas de estado (`HEAP_XMIN_COMMITTED`, `HEAP_XMAX_INVALID`, etc.).

```text
  Tupla Física en Página Heap:
  ┌─────────┬─────────┬──────────────┬──────────────────┬─────────────────────────────┐
  │ xmin    │ xmax    │ ctid         │ infomask         │ Datos de usuario (columnas) │
  │ (tx_id) │ (tx_id) │ (page, item) │ (commit flags)   │ customer_id, company_name...│
  └─────────┴─────────┴──────────────┴──────────────────┴─────────────────────────────┘
```

#### Ciclo de Vida de una Actualización (UPDATE)
Cuando se ejecuta `UPDATE customers SET contact_name = 'Nuevo' WHERE customer_id = 'ALFKI'`:
1. PostgreSQL **no sobrescribe** los bytes de la fila original en el disco.
2. Marca la tupla original con `xmax = ID_TRANSACCION_ACTUAL` (convirtiéndola en **Dead Tuple** para transacciones futuras una vez confirmada).
3. Inserta una **nueva tupla física** con `xmin = ID_TRANSACCION_ACTUAL`, `xmax = 0`, y actualiza el `ctid` de la tupla vieja apuntando a la nueva.
4. El espacio de las tuplas muertas permanece ocupado hasta que el proceso **`Autovacuum`** limpie los punteros.

#### El Rol del Visibility Map (VM) y los Index-Only Scans
- Cada tabla tiene un archivo de mapa de visibilidad (`_vm`).
- Contiene 2 bits por cada página de 8KB del Heap:
  - **Bit 0 (All-Visible):** Indica si todas las tuplas de la página son visibles para todas las transacciones activas (no hay tuplas muertas).
  - **Bit 1 (All-Frozen):** Indica si todas las tuplas han sido congeladas para prevenir el *Transaction ID Wraparound*.
- **`Index-Only Scan`:** Cuando una consulta solicita columnas que residen íntegramente en un índice B-Tree, PostgreSQL verifica el Visibility Map. Si la página del Heap está marcada como *All-Visible*, el motor **no lee el Heap en absoluto**, entregando el dato directo desde el índice en RAM.

```sql
-- Monitoreo de Tuplas Muertas (Dead Tuples) y Bloat en el Esquema
SELECT 
    schemaname,
    relname AS tabla,
    n_live_tup AS tuplas_vivas,
    n_dead_tup AS tuplas_muertas,
    round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 2) AS pct_bloat,
    last_vacuum,
    last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

### 8.3 Ciclo de Vida y Pipeline Lógico de Procesamiento SQL (12 Fases)

Una de las fuentes más comunes de errores de diseño y comprensión en SQL es confundir el **orden sintáctico** (cómo se escribe una consulta) con el **orden lógico de procesamiento** (la secuencia matemática en que el estándar relacional evalúa las cláusulas).

```text
========================================================================================================================
                                PIPELINE LÓGICO DE PROCESAMIENTO SQL (POSTGRESQL ENGINE)
========================================================================================================================
  [1. FROM]       ──► Localiza tablas base, evalúa subconsultas del FROM y genera producto cartesiano inicial
  [2. ON]         ──► Evalúa condiciones de cruce booleano por cada combinación de tuplas
  [3. JOIN]       ──► Aplica preservación de filas (LEFT/RIGHT/FULL OUTER) y genera relación intermedia
  [4. WHERE]      ──► Filtra tuplas individuales ANTES de cualquier agregación (no ve alias de SELECT ni agregados)
  [5. GROUP BY]   ──► Colapsa tuplas en cubetas/grupos según claves de agregación (HashAggregate / GroupAggregate)
  [6. HAVING]     ──► Filtra grupos completos evaluando predicados sobre funciones agregadas (COUNT, SUM, AVG)
  [7. WINDOW]     ──► Evalúa funciones de ventana (OVER: PARTITION BY, ORDER BY, ROWS/RANGE BETWEEN)
  [8. SELECT]     ──► Evalúa expresiones escalares, calcula proyecciones de columnas y asigna ALIAS
  [9. DISTINCT]   ──► Elimina duplicados de las tuplas proyectadas (Unique / HashAggregate)
  [10. SET OPS]   ──► Combina flujos de resultados independientes con UNION, INTERSECT o EXCEPT
  [11. ORDER BY]  ──► Ordena el conjunto final (Sort / Incremental Sort / Top-N Heap) -> ¡SÍ VE ALIAS DE SELECT!
  [12. LIMIT/OFF] ──► Acota el número de tuplas devueltas y descarta el desfase (Limit node)
========================================================================================================================
```

#### Desglose Técnico de las 12 Fases

1. **Fase 1 (`FROM`):** Se identifican los conjuntos de datos de origen (tablas base, vistas, subconsultas, `generate_series`). Si hay múltiples tablas separadas por comas, se genera el producto cartesiano conceptual ($R_1 \times R_2$).
2. **Fase 2 (`ON`):** En operaciones `JOIN`, el predicado de cruce filtra las combinaciones del producto cartesiano que satisfacen la condición booleana.
3. **Fase 3 (`JOIN`):** Si es un `OUTER JOIN` (`LEFT`, `RIGHT`, `FULL`), las filas no coincidentes del lado preservado se reinsertan en el flujo con valores `NULL` en los atributos de la tabla opuesta.
4. **Fase 4 (`WHERE`):** Se evalúa el predicado fila por fila sobre el flujo combinado. Las filas que evalúan a `FALSE` o `NULL` son descartadas inmediatamente. **Esta fase ocurre ANTES de cualquier agregación y no tiene acceso a los alias de `SELECT`**.
5. **Fase 5 (`GROUP BY`):** Las tuplas sobrevivientes se particionan en grupos discretos basados en los valores únicos de las columnas de agrupación.
6. **Fase 6 (`HAVING`):** Se aplican filtros a nivel de grupo. Permite expresiones que involucran funciones de agregación (`COUNT(*) > 5`, `SUM(freight) > 1000`).
7. **Fase 7 (`WINDOW`):** Se calculan las funciones analíticas de ventana (`ROW_NUMBER()`, `RANK()`, `SUM() OVER (...)`). Se ejecutan sobre las particiones definidas en `OVER()` manteniendo el grano individual de las filas.
8. **Fase 8 (`SELECT`):** Se proyectan las columnas solicitadas, se ejecutan las expresiones escalares matemáticas y de texto, y se asignan los nombres de alias a cada columna.
9. **Fase 9 (`DISTINCT`):** Se eliminan filas duplicadas del conjunto proyectado utilizando ordenamiento o tablas hash en memoria.
10. **Fase 10 (`SET OPERATIONS`):** Si la consulta utiliza operadores de conjuntos (`UNION`, `UNION ALL`, `INTERSECT`, `EXCEPT`), se combinan los flujos de las consultas independientes.
11. **Fase 11 (`ORDER BY`):** Se ordena el conjunto de resultados final. Como la Fase 8 (`SELECT`) ya se ejecutó, **`ORDER BY` tiene visibilidad completa sobre los alias asignados en `SELECT`**.
12. **Fase 12 (`LIMIT / OFFSET`):** El nodo de límite descarta las primeras $K$ filas (`OFFSET`) y devuelve únicamente las siguientes $N$ tuplas (`LIMIT`) hacia el cliente.

### 8.4 Matriz de Ámbito y Visibilidad de Identificadores y Alias

La siguiente matriz define taxativamente qué elementos del lenguaje pueden ser referenciados en cada cláusula de una sentencia SQL en PostgreSQL:

| Cláusula SQL | Fase | ¿Acceso a Columnas de Tablas? | ¿Acceso a Alias de `SELECT`? | ¿Permite Funciones Agregadas? (`SUM`, `COUNT`) | ¿Permite Funciones de Ventana? (`OVER`) |
|---|:---:|:---:|:---:|:---:|:---:|
| `FROM / JOIN / ON` | 1–3 | ✅ Sí | ❌ No | ❌ No | ❌ No |
| `WHERE` | 4 | ✅ Sí | ❌ No | ❌ No | ❌ No |
| `GROUP BY` | 5 | ✅ Sí | ❌ No (en SQL estándar) | ❌ No | ❌ No |
| `HAVING` | 6 | ✅ Sí (si está en GROUP BY) | ⚠️ Solo en PG 15+ (no portable) | ✅ Sí | ❌ No |
| `WINDOW` | 7 | ✅ Sí | ❌ No | ✅ Sí (agregados sobre partición) | ❌ No anidadas |
| `SELECT` | 8 | ✅ Sí | ❌ No entre sí (mismo nivel) | ✅ Sí | ✅ Sí |
| `DISTINCT` | 9 | ✅ Sí | ✅ Sí | ✅ Sí | ✅ Sí |
| `SET OPS` (`UNION`) | 10 | ❌ No (solo flujos SELECT) | ❌ No | ❌ No | ❌ No |
| `ORDER BY` | 11 | ✅ Sí | ✅ Sí (estándar y PG) | ✅ Sí | ✅ Sí |
| `LIMIT / OFFSET` | 12 | ❌ No (solo literales/parámetros) | ❌ No | ❌ No | ❌ No |

#### Preguntas Críticas de Arquitectura sobre Visibilidad

##### 1. ¿Por qué `WHERE` no puede ver los alias definidos en `SELECT`?
Porque en el pipeline relacional, el filtrado `WHERE` (Fase 4) ocurre antes de que la proyección y el etiquetado de columnas `SELECT` (Fase 8) hayan sido evaluados. Si el motor intentara resolver un alias de `SELECT` en `WHERE`, incurriría en una dependencia circular en consultas con transformaciones de datos complejas.

##### 2. ¿Por qué `ORDER BY` sí puede ver los alias de `SELECT`?
Porque el ordenamiento `ORDER BY` (Fase 11) ocurre después de la proyección `SELECT` (Fase 8). En esa etapa, el motor ya construyó la tupla proyectada con sus nombres de salida definitivos.

##### 3. ¿Dónde y por qué se evalúan las funciones de ventana en la Fase 7?
Las funciones de ventana necesitan que el conjunto ya esté filtrado por `WHERE` y agrupado/colapsado por `GROUP BY`/`HAVING`, pero requieren calcular métricas analíticas a nivel de fila antes de que `SELECT` proyecte los campos finales y `DISTINCT` elimine duplicados. Por esta razón no se pueden colocar funciones de ventana directamente dentro del `WHERE` ni del `HAVING`.

### 8.5 Orden Lógico vs Plan de Ejecución Físico (El Rol del Optimizador CBO)

Es fundamental distinguir entre:
1. **Orden Lógico (Semántica Declarativa):** El estándar formal que define *qué* resultado matemático debe producir la consulta.
2. **Plan Físico (Motor de Ejecución):** El árbol de operadores físicos que el Optimizador Basado en Costos (CBO) de PostgreSQL decide ejecutar para obtener ese resultado en el menor tiempo posible.

#### El Optimizador Basado en Costos (CBO)
El optimizador puede reordenar las operaciones físicas siempre que el resultado lógico se preserve intacto:
- **Predicate Pushdown:** Empuja condiciones del `WHERE` al nivel más bajo posible del escaneo (`Index Cond` o `Filter` durante el `Seq Scan`) para no cargar páginas innecesarias en `shared_buffers`.
- **Join Reordering:** Cambia el orden físico de unión de las tablas (ej. uniendo la tabla más pequeña primero para construir una tabla hash compacta en `work_mem`).
- **HashAggregate vs GroupAggregate:** Si las claves de agregación no están indexadas, usa `HashAggregate`; si los datos ya vienen ordenados por un índice B-Tree, usa `GroupAggregate` con costo de memoria casi nulo.

`EXPLAIN (ANALYZE, BUFFERS)` permite auditar exactamente cómo el planificador tradujo la consulta lógica a operaciones físicas de CPU y memoria.

## 9. Convenciones y Estándares en PostgreSQL

PostgreSQL dispone de funcionalidades avanzadas del estándar SQL y extensiones nativas de alto rendimiento. Estas convenciones son las que aplicaremos en todo el laboratorio porque constituyen las **buenas prácticas de ingeniería de datos en la industria**.

### 9.1 RETURNING (DML con Proyección Inmediata)

**`RETURNING` devuelve los valores de las tuplas afectadas por un `INSERT`, `UPDATE` o `DELETE`**, evitando una consulta `SELECT` posterior y reduciendo la latencia de red.

| PostgreSQL (con RETURNING) | MySQL / Otros (sin RETURNING) |
|---------------------------|----------------------|
| 1 query: `INSERT ... RETURNING id` | 1er query: `INSERT ...` |
| Obtienes las columnas calculadas inmediatamente | 2do query: `SELECT LAST_INSERT_ID()` o `SELECT ...` |
| **1 roundtrip a la base de datos** | **2 roundtrips a la base de datos** |

```sql
-- PostgreSQL: eficiente con RETURNING
INSERT INTO customers (customer_id, company_name, city, country)
VALUES ('NEWCO', 'Nueva Corp', 'Lima', 'Peru')
RETURNING customer_id, company_name, city;
```

### 9.2 ON CONFLICT (UPSERT Atómico)

**`ON CONFLICT` ejecuta una inserción o actualización atómica** si existe una colisión de clave única o primaria. En el esquema canónico de Northwind, la columna `discontinued` de `products` es `NOT NULL` (entero 0 o 1), por lo que debe incluirse explícitamente:

```sql
-- PostgreSQL: UPSERT limpio con DDL Northwind (discontinued NOT NULL)
INSERT INTO products (product_id, product_name, unit_price, discontinued)
VALUES (100, 'Producto Nuevo', 15.50, 0)
ON CONFLICT (product_id)
DO UPDATE SET
  product_name = EXCLUDED.product_name,
  unit_price = EXCLUDED.unit_price,
  discontinued = EXCLUDED.discontinued;

-- Ignorar conflicto silenciosamente si la tupla ya existe
INSERT INTO products (product_id, product_name, unit_price, discontinued)
VALUES (100, 'Producto Nuevo', 15.50, 0)
ON CONFLICT (product_id) DO NOTHING;
```

> **`EXCLUDED`** es una pseudotabla especial que contiene los valores que **iban a ser insertados**. Permite referenciar la fila propuesta para actualizar los campos deseados.

### 9.3 ILIKE (Búsqueda Textual Case-Insensitive)

**`ILIKE` realiza comparaciones de cadenas ignorando mayúsculas y minúsculas** de forma nativa en PostgreSQL:

```sql
-- PostgreSQL: case-insensitive nativo
SELECT customer_id, company_name, city 
FROM customers 
WHERE company_name ILIKE '%food%';
```

### 9.4 FILTER (Agregación Condicional Declarativa)

**`FILTER (WHERE ...)` permite acumular métricas condicionales dentro de funciones agregadas**, evitando la sobrecarga de subconsultas o sintaxis compleja de `CASE WHEN`:

```sql
-- Agregación condicional elegante con FILTER
SELECT
  COUNT(*) AS total_pedidos,
  COUNT(*) FILTER (WHERE ship_country = 'USA') AS pedidos_usa,
  COUNT(*) FILTER (WHERE ship_country = 'Germany') AS pedidos_alemania,
  COUNT(*) FILTER (WHERE ship_country = 'Brazil') AS pedidos_brasil
FROM orders;
```

### 9.5 GENERATED ALWAYS AS IDENTITY vs SERIAL

`GENERATED ALWAYS AS IDENTITY` es la especificación estándar de SQL (soportada desde PostgreSQL 10) que reemplaza al pseudotipo heredado `SERIAL`:

```sql
-- Estándar SQL moderno (recomendado en producción)
CREATE TABLE inventario_log (
  log_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  detalle TEXT NOT NULL,
  registrado_en TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

### 9.6 Manejo de Ámbitos y Subconsultas para Alias de SELECT

Dado que la cláusula `WHERE` se evalúa en la **Fase 4** y la cláusula `SELECT` en la **Fase 8**, un alias proyectado en `SELECT` no existe durante la evaluación del `WHERE`.

```sql
-- Error conceptual de ámbito:
SELECT
  od.order_id,
  od.unit_price * od.quantity AS total
FROM order_details od
WHERE total > 100;  -- ❌ ERROR: column "total" does not exist

-- Solución 1: Repetir la expresión escalar en WHERE
SELECT
  od.order_id,
  od.unit_price * od.quantity AS total
FROM order_details od
WHERE (od.unit_price * od.quantity) > 100;  -- ✅ Válido

-- Solución 2: Subconsulta derivada (el alias se materializa en el FROM externo)
SELECT sub.order_id, sub.total
FROM (
  SELECT
    od.order_id,
    od.unit_price * od.quantity AS total
  FROM order_details od
) sub
WHERE sub.total > 100;  -- ✅ Válido

-- Solución 3: Con JOIN a products para proyectar el nombre del producto
SELECT
  p.product_name,
  od.unit_price * od.quantity AS total
FROM order_details od
JOIN products p ON od.product_id = p.product_id
WHERE (od.unit_price * od.quantity) > 100;  -- ✅ Válido
```

### 9.7 Transaccionalidad Segura para DML Destructivo con EXPLAIN

Nunca ejecutes un `DELETE` o `UPDATE` masivo en producción sin auditar antes el volumen de filas afectadas:

```sql
-- Patrón seguro: auditar el plan y filas afectadas sin alterar el estado persistente
BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
DELETE FROM orders WHERE order_date < '1990-01-01';
-- Verifica el número de filas afectadas en el plan
ROLLBACK;  -- Revierte inmediatamente sin persistir cambios
```

### 9.8 CTEs con MATERIALIZED y NOT MATERIALIZED Hints

> **Tratado de Referencia:** Hans-Jürgen Schönig (*Mastering PostgreSQL 16*, Cap. 4: Advanced SQL & Optimization).

Desde PostgreSQL 12, el motor modificó su comportamiento histórico de "barrera de optimización" (*Optimization Fence*). Ahora, PostgreSQL realiza **inlining automático** (desarma la CTE e integra sus predicados al plan principal) si y solo si se cumplen las siguientes 3 condiciones formales:
1. La subconsulta CTE **no contiene funciones volátiles** (`random()`, `timeofday()`, `nextval()`).
2. No contiene comandos de modificación DML con cláusula `RETURNING`.
3. Es referenciada **exactamente una sola vez** en la consulta exterior.

Si una CTE se referencia 2 o más veces, PostgreSQL revierte por defecto a materializarla en memoria para evitar recomputarla. Con las cláusulas explícitas podemos controlar este comportamiento:

```sql
-- MATERIALIZED: fuerza a calcular la CTE una sola vez en memoria, aislando su plan
WITH ventas_resumen AS MATERIALIZED (
  SELECT product_id, SUM(quantity * unit_price) AS total_ventas
  FROM order_details
  GROUP BY product_id
)
SELECT p.product_name, v.total_ventas
FROM ventas_resumen v
JOIN products p ON v.product_id = p.product_id
WHERE v.total_ventas > 5000;

-- NOT MATERIALIZED: permite al optimizador empujar predicados WHERE (Predicate Pushdown) al interior de la CTE
WITH productos_activos AS NOT MATERIALIZED (
  SELECT product_id, product_name, unit_price
  FROM products
  WHERE discontinued = 0
)
SELECT * FROM productos_activos WHERE unit_price > 50;
```

### 9.9 generate_series (Generación de Series Temporales y Tabulares)

`generate_series()` genera secuencias enteras o temporales bajo demanda, indispensable para rellenar vacíos cronológicos en reportes:

```sql
-- Reporte cronológico continuo: detecta días sin ventas
SELECT
  d::date AS fecha_calendario,
  COUNT(o.order_id) AS total_pedidos
FROM generate_series('1996-07-01'::date, '1996-07-15'::date, '1 day'::interval) d
LEFT JOIN orders o ON o.order_date = d::date
GROUP BY d::date
ORDER BY d::date;
```

### 9.10 Encuadre de Ventanas Riguroso: ROWS vs RANGE vs GROUPS y Cláusula EXCLUDE

> **Tratados de Referencia:** Dimitri Fontaine (*The Art of PostgreSQL*, Cap. 5), Markus Winand (*SQL Performance Explained*), Itzik Ben-Gan (*High-Performance SQL Using Window Functions*).

Al utilizar funciones de ventana con `ORDER BY`, el estándar ISO/IEC SQL y PostgreSQL aplican por defecto un marco (*Window Frame*):
$$\text{DEFAULT: } \mathbf{RANGE\ BETWEEN\ UNBOUNDED\ PRECEDING\ AND\ CURRENT\ ROW}$$

#### Comparación Técnica de los 3 Modos de Encuadre

| Modo de Encuadre | Mecánica de Desplazamiento | Manejo de Empates (*Peer Groups*) | Eficiencia en Memoria / CPU |
| :--- | :--- | :--- | :--- |
| **`ROWS`** | Filas físicas individuales | Trata cada fila por separado según su posición física | ⚡ **Óptima** (Punteros directos en el nodo `WindowAgg`) |
| **`RANGE`** | Rango de valores lógicos del `ORDER BY` | Acumula en bloque a todas las tuplas que compartan el mismo valor | ⚠️ **Media** (Requiere evaluar el grupo de pares completo) |
| **`GROUPS`** (PG11+) | Grupos de filas con valores idénticos | Avanza por $N$ grupos de pares en lugar de $N$ filas físicas | ⚡ **Alta** (Ideal para agrupaciones lógicas) |

```sql
-- Demostración de acumulación fila por fila vs en bloque por empates de fecha
SELECT 
    order_id,
    order_date,
    freight,
    -- ROWS: acumula exactamente fila a fila (sin importar empates en order_date)
    SUM(freight) OVER (
        ORDER BY order_date, order_id 
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS acumulado_estricto_rows,
    -- RANGE: acumula en bloque a todas las órdenes con la misma fecha
    SUM(freight) OVER (
        ORDER BY order_date 
        RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS acumulado_por_fecha_range
FROM orders
LIMIT 10;
```

#### Cláusula Estándar EXCLUDE (Exclusiones de Marco)
PostgreSQL soporta la cláusula `EXCLUDE` para descartar subconjuntos dentro del marco de la ventana:
- `EXCLUDE CURRENT ROW`: Excluye la fila actual del cálculo.
- `EXCLUDE GROUP`: Excluye la fila actual y todos sus pares con el mismo valor en `ORDER BY`.
- `EXCLUDE TIES`: Excluye los pares de la fila actual, pero mantiene la fila actual en el cálculo.
- `EXCLUDE NO OTHERS` (Default): No excluye ninguna fila del marco.

### 9.11 Transacciones, Anomalías de Concurrencia y Aislamiento SSI

> **Tratados de Referencia:**  
> - Martin Kleppmann (2017): *Designing Data-Intensive Applications* (Capítulo 7: Transactions).  
> - Hal Berenson et al. (1995): *A Critique of ANSI SQL Isolation Levels* (ACM SIGMOD).

#### Taxonomía de Fenómenos y Anomalías Transaccionales

| Fenómeno / Anomalía | Código Formal | Descripción Técnica | Prevenido en PostgreSQL por |
| :--- | :---: | :--- | :--- |
| **Dirty Read** | $A1 / P1$ | Leer datos no confirmados (*uncommitted*) de otra transacción. | `Read Committed` (PG nunca permite Dirty Reads por MVCC) |
| **Non-Repeatable Read** | $A2 / P2$ | Volver a leer la misma fila y encontrar valores modificados por otra tx confirmada. | `Repeatable Read` (Snapshot Isolation) |
| **Phantom Read** | $A3 / P3$ | Una consulta de rango encuentra nuevas filas insertadas por otra tx confirmada. | `Repeatable Read` (En PG, Snapshot Isolation previene fantasmas) |
| **Lost Update** | $P4$ | Dos transacciones concurrentes sobrescriben el mismo registro perdiendo una actualización. | `Repeatable Read` / `SELECT ... FOR UPDATE` |
| **Write Skew** | $A5B$ | Dos transacciones leen los mismos datos, toman decisiones válidas individualmente, pero sus escrituras combinadas violan una regla de negocio global. | 🛡️ **`SERIALIZABLE` (SSI)** |

#### Cómo Opera Serializable Snapshot Isolation (SSI) en PostgreSQL
A diferencia de los motores basados en bloqueos pesimistas de dos fases (2PL) que detienen las lecturas, PostgreSQL implementa **SSI**:
1. Cada transacción opera sobre su propio *Snapshot* en memoria a velocidad nativa de MVCC.
2. El motor mantiene una estructura en memoria de bloqueos virtuales llamados **`SIREAD locks`** (rastrean dependencias de lectura contra predicados).
3. Si el motor detecta un ciclo de anti-dependencias (*rw-antidependencies* simultáneas) que produciría un estado inconsistente (*Write Skew*), aborta automáticamente a una de las transacciones con:  
   `ERROR: could not serialize access due to read/write dependencies among transactions (SQLSTATE 40001)`.
4. La aplicación cliente únicamente debe capturar el error `40001` y reintentar la transacción.

## 11. Banco de Preguntas Conceptuales para Entrevistas Técnicas (Data Engineer / DBA)

Esta sección reúne las preguntas técnicas más frecuentes y decisivas que un **Lead Data Engineer** o **Principal Architect** formula en entrevistas de selección, con respuestas fundamentadas en los libros de referencia de la industria:

---

### P1: ¿Por qué `COUNT(*)` en PostgreSQL puede ser más lento que en otros motores como MySQL (MyISAM)?
- **Respuesta de Nivel Master:** Debido a la arquitectura **MVCC (Multi-Version Concurrency Control)** de PostgreSQL. No existe un contador global estático porque cada transacción activa tiene una visibilidad distinta de las tuplas basada en su snapshot (`xmin`/`xmax`). PostgreSQL debe escanear el mapa de visibilidad (*Visibility Map*) o las páginas del Heap para determinar qué filas son visibles para la transacción actual.
- **Libro de Referencia:** *Designing Data-Intensive Applications* (Martin Kleppmann) & *PostgreSQL 16 High Performance* (Gregory Smith).

---

### P2: ¿Cuál es la diferencia técnica entre un `Index Scan`, un `Bitmap Index Scan` y un `Index Only Scan`?
- **Respuesta de Nivel Master:**
  1. **`Index Scan`:** Lee el árbol B-Tree nodo a nodo y accede al Heap inmediatamente por cada tupla (eficiente para alta selectividad, 1 a 10 filas).
  2. **`Bitmap Index Scan`:** Lee el índice, construye un mapa de bits de punteros a páginas en memoria, ordena las páginas físicamente y luego accede al Heap en lecturas secuenciales reduciendo el movimiento del cabezal de disco.
  3. **`Index Only Scan`:** Lee exclusivamente los datos desde las páginas del índice sin tocar el Heap en absoluto (habilitado si todas las columnas solicitadas están en el índice y el *Visibility Map* confirma que la página no tiene tuplas muertas).
- **Libro de Referencia:** *SQL Performance Explained* (Markus Winand).

---

### P3: ¿Cómo optimizarías una consulta con `JOIN` que está realizando un `Nested Loop` extremadamente lento?
- **Respuesta de Nivel Master:**
  1. Verificar si la clave foránea en la tabla interna tiene un índice B-Tree (un Nested Loop sin índice ejecuta $\mathcal{O}(N \times M)$).
  2. Comprobar si las estadísticas de la tabla están desactualizadas ejecutando `ANALYZE`.
  3. Aumentar el parámetro `work_mem` para que el optimizador tenga memoria suficiente para construir una tabla hash y elegir un **`Hash Join`** ($\mathcal{O}(N + M)$).
- **Libro de Referencia:** *Mastering PostgreSQL 16* (Hans-Jürgen Schönig).

---

### P4: ¿Por qué ocurre el fenómeno de "Table Bloat" y cómo opera el `Autovacuum`?
- **Respuesta de Nivel Master:** En PostgreSQL, los `UPDATE` insertan una nueva versión de la fila y los `DELETE` marcan la tupla como muerta (`xmax`). El espacio físico en las páginas de 8KB no se libera inmediatamente al sistema operativo. El demonio **`Autovacuum`** escanea periódicamente las páginas, limpia los punteros a tuplas muertas para que el espacio pueda ser reutilizado por nuevos `INSERT` y actualiza las estadísticas de `pg_statistic`.
- **Libro de Referencia:** *PostgreSQL 16 High Performance* (Gregory Smith).

---

### P5: ¿Qué diferencia existe entre un CTE con `MATERIALIZED` y `NOT MATERIALIZED`?
- **Respuesta de Nivel Master:**
  - **`AS MATERIALIZED`:** Fuerza a PostgreSQL a evaluar la subconsulta una sola vez y guardarla como una tabla temporal en memoria, actuando como una barrera de optimización (útil si la CTE es costosa y se referencia múltiples veces).
  - **`AS NOT MATERIALIZED` (Inline):** Permite al planificador "desarmar" la CTE y empujar predicados `WHERE` hacia adentro (*Predicate Pushdown*), fusionando los árboles de ejecución para aprovechar índices.
- **Libro de Referencia:** *The Art of PostgreSQL* (Dimitri Fontaine).

---

### P6: ¿Cuándo conviene utilizar un índice `BRIN` en lugar de un `B-Tree`?
- **Respuesta de Nivel Master:** En tablas masivas (cientos de millones o billones de filas) donde los datos se insertan cronológicamente y están físicamente correlacionados con el disco (como timestamps de logs o IDs secuenciales). Un índice `BRIN` (Block Range Index) ocupa solo kilobytes en lugar de gigabytes, resumiendo los valores mínimos y máximos por rango de páginas.
- **Libro de Referencia:** *Mastering PostgreSQL 16* (Hans-Jürgen Schönig).

---

### P7: ¿Qué es una anomalía de serialización (Serialization Anomaly) y cómo se previene?
- **Respuesta de Nivel Master:** Ocurre cuando transacciones concurrentes en nivel `Repeatable Read` generan un estado final que no podría haber ocurrido en ninguna ejecución puramente secuencial (ej. *Write Skew*). Se previene elevando el nivel de aislamiento a **`SERIALIZABLE`** (SSI - Serializable Snapshot Isolation) o mediante bloqueos explícitos pesimistas (`SELECT ... FOR UPDATE`).
- **Libro de Referencia:** *Designing Data-Intensive Applications* (Martin Kleppmann).

## 12. Glosario Técnico

| Término | Definición Formal | Contexto en PostgreSQL 16 |
|---------|-------------------|---------------------------|
| **ACID** | Atomicidad, Consistencia, Aislamiento, Durabilidad | Conjunto de propiedades que garantizan la confiabilidad de las transacciones de base de datos. |
| **Autovacuum** | Proceso de fondo automático que limpia tuplas muertas | Previene el bloat y actualiza las estadísticas del catálogo (`pg_statistic`). |
| **B-Tree** | Árbol balanceado ($\mathcal{O}(\log N)$) | Estructura de índice por defecto para igualdad (=), rangos (<, >) y ordenamiento (`ORDER BY`). |
| **Bitmap Index Scan** | Escaneo en dos fases mediante mapa de bits en memoria | Combina múltiples condiciones indexadas y optimiza el acceso secuencial al Heap. |
| **Bloat** | Espacio físico ocupado por tuplas muertas en disco | Fragmentación interna resultante de operaciones `UPDATE` y `DELETE` frecuentes. |
| **BRIN** | Block Range Index | Índice ultracompacto para tablas de series temporales ordenadas correlacionadas con el disco. |
| **Buffer Pool** | Área de memoria compartida (`shared_buffers`) | Caché en RAM de páginas de 8KB de tablas Heap e índices. |
| **CBO** | Cost-Based Optimizer | Componente del motor que estima el costo computacional de múltiples planes y elige el óptimo. |
| **Covering Index** | Índice con cláusula `INCLUDE` | Contiene columnas adicionales sin ordenarlas para permitir *Index Only Scans*. |
| **CTE** | Common Table Expression (`WITH`) | Estructura que define un conjunto de resultados temporal con soporte recursivo (`WITH RECURSIVE`). |
| **GIN** | Generalized Inverted Index | Índice invertido para tipos compuestos, arrays, búsqueda Full-Text y documentos `JSONB`. |
| **GiST** | Generalized Search Tree | Estructura de árbol balanceado extensible para datos geométricos, PostGIS y solapamiento de rangos (`&&`). |
| **Hash Join** | Algoritmo de unión basado en tabla hash en memoria | Construye una tabla hash de la relación más pequeña en `work_mem` y escanea la mayor. |
| **HOT** | Heap-Only Tuples | Optimización que permite actualizar tuplas dentro de la misma página sin modificar los índices. |
| **Index-Only Scan** | Acceso a datos directo desde las páginas del índice | Elimina lecturas al Heap cuando el *Visibility Map* confirma que la página es *All-Visible*. |
| **MVCC** | Multi-Version Concurrency Control | Modelo de concurrencia que mantiene múltiples versiones de tuplas para evitar bloqueos de lectura. |
| **Predicate Pushdown** | Técnica de optimización de consultas | Empuja los filtros `WHERE` lo más cerca posible del almacenamiento para minimizar I/O. |
| **SSI** | Serializable Snapshot Isolation | Implementación de aislamiento `SERIALIZABLE` sin bloqueos pesimistas basada en detección de conflictos SIREAD. |
| **Visibility Map (VM)** | Mapa de bits por cada página de 8KB del Heap | Registra si una página contiene solo tuplas visibles para todas las transacciones activas. |
| **WAL** | Write-Ahead Logging | Registro secuencial de cambios en disco antes de modificarlos en el Heap para garantizar durabilidad (`fsync`). |
| **work_mem** | Asignación de memoria por proceso y operación | Memoria privada para operaciones de ordenamiento y tablas hash antes de derramar a disco. |
